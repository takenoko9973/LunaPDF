# LunaPDF Windows配布対応 指示書

## 目的

LunaPDFをWindows 11上で日常的に利用できるよう、以下の2種類の配布物を生成できる状態にする。

1. インストーラー版
2. ポータブル版

また、GitHub Actions上でWindows向けReleaseビルドと両配布物の生成を実行できるようにする。

現時点では個人利用のみを対象とする。一般公開・企業配布に必要な高度な配布機能は対象外とする。

---

## 対象リポジトリ

* Repository: `takenoko9973/LunaPDF`
* 主対象OS: Windows 11
* 対象アーキテクチャ: x86_64
* アプリケーション: Rust製PDFビューアー
* 既定ブランチ: `main`

作業開始時に必ずリポジトリの最新状態を取得し、現在の構成、依存関係、起動処理、設定保存処理、タブ管理処理、Windows固有処理の有無を確認すること。

過去の構成を前提にせず、実際の最新コードを根拠として調査・設計すること。

---

## 基本方針

具体的なライブラリ、ディレクトリ構成、IPC方式、Windows API、インストーラー設定、GitHub Actionsの構成は、Codex側で現状を調査したうえで決定すること。

本指示書に記載されたコード例や特定方式をそのまま採用するのではなく、現在のLunaPDFの設計に適合する方法を選択すること。

以下を重視する。

* 既存アーキテクチャと責務分離を維持する
* Windows固有処理をUIやドメインロジックへ混在させない
* 不要な型、抽象化、依存関係を増やさない
* 一つの巨大な型やモジュールへ責務を集中させない
* インストーラー版とポータブル版で可能な限り共通の実行ファイルを使用する
* ローカル開発環境を不必要に変更しない
* LinuxやmacOS向けコードを不必要に破壊しない
* 未確認事項を推測で補わず、実際にビルド・実行・調査して判断する

# 1. 事前調査と実装計画

実装前に、少なくとも以下を調査すること。

* 現在のWindows向けReleaseビルド方法
* `Cargo.toml`に設定されたRustバージョンと依存関係
* MuPDFおよびネイティブ依存関係のビルド条件
* 実行時に外部ファイルやDLLを必要とするか
* PDFファイルをコマンドライン引数から開く現在の処理
* 複数のPDFパスを渡した場合の挙動
* タブ追加処理を外部要求から呼び出せる構造になっているか
* セッション、設定、キャッシュ等の保存先
* アプリケーションアイコンの現在の管理方法
* Windows向けリソース埋め込みの有無
* 既存のGitHub Actions workflowの有無
* インストーラー版とポータブル版で設定保存先を分離する必要性

調査後、実装に入る前に以下を提示すること。

1. 現状整理
2. 採用する構成
3. 変更対象
4. 追加する依存関係
5. 既存コードへの影響
6. 想定される問題
7. 検証方法

特に、設定保存方式と単一インスタンス方式は既存設計への影響が大きいため、実装前に責務とデータフローを明確にすること。

# 2. Windows向け実行ファイルの整備

Windows向けReleaseビルド成果物を、通常のデスクトップアプリケーションとして利用できる状態にすること。

必要な要件は以下のとおり。

* Release版起動時に不要なコンソールウィンドウを表示しない
* LunaPDFのアプリケーションアイコンを設定する
* ウィンドウ、実行ファイル、ショートカット、インストーラーでアイコンを統一する
* Windows Explorer上で実行ファイルに適切な製品情報が表示されるようにする
* アプリケーション名、バージョン、説明等を適切に設定する
* バージョン情報の重複管理をできる限り避ける
* デバッグビルドの開発体験を損なわない
* Windows以外のビルドへWindows固有設定を波及させない

アイコンの元データ、必要サイズ、リソース生成方法については、現在のアセット構成を調査して決定すること。

アイコン素材が不足している場合は、必要な入力ファイルと形式を明示すること。仮の低品質アイコンを最終成果物として固定しないこと。

---

# 3. PDFファイル起動対応の検証と改善

WindowsからPDFファイルを渡された際に、LunaPDFが正常に開けることを保証する。

少なくとも以下を検証すること。

* PDFファイルを1つ指定して起動
* 複数のPDFファイルを同時に指定して起動
* 空白を含むパス
* 日本語を含むパス
* 長いパス
* 相対パスと絶対パス
* 存在しないファイル
* PDF以外のファイル
* 同じPDFが既に開かれている場合
* 起動引数がない場合

異常な入力によってアプリ全体がクラッシュしないようにする。

エラーの通知方法は、現在のLunaPDFのエラー処理とUI設計を確認して決定すること。

---

# 4. 単一インスタンスと既存ウィンドウへのファイル転送

PDFの既定アプリとして利用する場合、PDFを開くたびに別ウィンドウが生成されるのではなく、原則として既存のLunaPDFへ新しいタブとして追加される挙動を実現する。

期待する挙動は以下のとおり。

1. LunaPDFが起動していない状態でPDFを開く
   → LunaPDFを起動し、そのPDFを表示する。

2. LunaPDFが既に起動している状態で別のPDFを開く
   → 既存プロセスへPDFパスを渡し、新しいタブとして開く。

3. 複数のPDFをまとめて開く
   → 既存ウィンドウ内に必要なタブを追加する。

4. ファイル転送後
   → 二重起動側のプロセスは正常終了する。

5. 既存ウィンドウが最小化または背面にある場合
   → 必要に応じてユーザーが操作可能な状態に戻す。

具体的な起動済み判定方法、プロセス間通信方式、排他制御、ウィンドウ前面化方法は、Windows上での信頼性、実装複雑度、既存依存関係との整合性を比較して決定すること。

以下の点を考慮すること。

* 同時に複数の起動要求が発生した場合
* 起動直後で受信側の初期化が完了していない場合
* IPC通信が失敗した場合
* 異常終了後に起動済み状態だけが残らないこと
* UIスレッドをブロックしないこと
* 受信した要求を既存のタブ管理経路へ安全に渡すこと
* 分割ビュー実装と干渉しないこと
* 同一ユーザー内でのみ通信すればよいこと

単一インスタンス機能を、インストーラーのレジストリ処理やUIコードへ直接結合しないこと。

# 5. インストーラー版

Windows向けインストーラーを生成する。

インストーラー方式は、個人利用、管理者権限不要、実装・保守コストを踏まえてCodex側で選定すること。ただし、過剰に複雑な配布方式は避ける。

## 必須要件

* 管理者権限なしでインストールできる
* ユーザー単位でインストールする
* 適切なユーザー領域へ配置する
* スタートメニューへLunaPDFを登録する
* デスクトップショートカットは任意選択とする
* アンインストール可能にする
* 同一アプリとして上書きインストールできる
* バージョンアップ時に別アプリ扱いにならない
* インストール完了後にLunaPDFを起動できる
* インストーラー自体にLunaPDFのアイコンを設定する
* アプリケーション本体と必要な実行時ファイルを過不足なく含める
* デバッグ用ファイルや不要な中間生成物を含めない
* 他のPDFビューアーの設定を破壊しない
* アンインストール時に他アプリの関連付けを変更しない

## 設定・セッションデータ

アンインストール時に、ユーザー設定、セッション、キャッシュ等を削除するか保持するかを整理すること。

個人利用では、通常のアンインストールでユーザーデータを保持してもよい。ただし、一時ファイルや不要なキャッシュを残すかどうかは調査して判断すること。

アプリケーション本体とユーザーデータの保存場所を混同しないこと。

---

# 6. PDF対応アプリとしての登録

インストーラー版を、Windows上でPDFを開けるアプリケーションとして登録する。

以下を満たすこと。

* PDFの「プログラムから開く」にLunaPDFが表示される
* Windowsの既定のアプリ設定でLunaPDFを選択できる
* PDFファイルをLunaPDFへ関連付けた場合、ファイルパスが正しく渡される
* LunaPDFのアイコンと表示名が適切に表示される
* アンインストール後にLunaPDFの登録が残らない
* 他のPDFアプリの登録を上書きまたは削除しない
* Windowsの既定アプリ保護機構を回避しない
* レジストリの`UserChoice`等を直接書き換えない
* インストールだけで既定アプリを強制変更しない

LunaPDF内には、Windowsの既定アプリ設定画面を開くための導線を追加すること。

配置場所と文言は、既存メニュー構成を確認して決定すること。Windows以外では表示しない、または適切に無効化すること。

Windowsのバージョン差異や設定URIの仕様は、公式資料を確認して実装すること。

---

# 7. ポータブル版

インストールせずに実行できるポータブル版を生成する。

## 必須要件

* ZIPを展開して実行できる
* 管理者権限を必要としない
* インストール処理を必要としない
* レジストリへファイル関連付けを登録しない
* Windowsの既定アプリを変更しない
* 実行に必要なファイルをZIP内へ含める
* 不要なビルド生成物を含めない
* ZIP内のトップレベル構成を分かりやすくする
* インストーラー版と同じLunaPDF本体を可能な限り使用する
* ZIPの展開先に空白や日本語が含まれていても動作する

## 設定保存方式

「ポータブル版」という名称で、設定まで実行ファイルの隣へ保存する完全なポータブルモードを実装するか、単にインストール不要版としてユーザー領域へ設定を保存するかを、既存の設定保存実装を調査して判断すること。

個人利用において複雑なモード切替が不要であれば、インストーラー版と同じユーザー設定保存先を使用してよい。

ただし、その場合はREADMEや成果物の説明で、以下を明確にすること。

* インストールは不要である
* 設定は実行ファイル横ではなくユーザー領域へ保存される可能性がある
* ZIPを削除しても設定が残る可能性がある

完全なポータブル設定保存を実装する場合は、環境変数、起動引数、マーカーファイル等の方式を比較し、既存構成への影響を説明すること。

本タスクでは、完全ポータブル化のために設定基盤を大幅に複雑化させることは避ける。

---

# 8. GitHub Actions

GitHub Actionsを用いて、Windows向け配布物を自動生成する。

## 生成対象

1回の配布用workflow実行で、少なくとも以下を生成すること。

* LunaPDFインストーラー
* LunaPDFポータブルZIP

ファイル名にはバージョンを含めること。

例：

* `LunaPDF-Setup-<version>-x64.exe`
* `LunaPDF-Portable-<version>-x64.zip`

実際の命名規則は、既存のプロジェクト命名と将来のタグ運用を考慮して決定すること。

## workflowの実行条件

当面は手動実行を必須とする。

* GitHub Actions画面から手動実行できる
* ブランチを指定して実行できる
* 個人利用のため、すべてのpushでインストーラーを生成する必要はない

将来タグを利用したRelease作成へ拡張しやすい構成にする。ただし、本タスクでGitHub Releaseの自動公開まで実装するかは、現在のworkflow構成と必要性を確認して判断すること。

少なくともAction Artifactとして生成物を取得できるようにする。

## workflowで行う処理

処理内容と順序はCodex側で設計するが、概ね以下を満たすこと。

* リポジトリのチェックアウト
* 必要なRust toolchainの設定
* 依存関係の取得
* Windows向けReleaseビルド
* 必要なテストまたは最低限のビルド検証
* インストーラー生成
* ポータブル版ディレクトリの構築
* ポータブルZIPの生成
* 生成物の存在確認
* Artifactへのアップロード

## バージョン

`Cargo.toml`等に定義されたアプリケーションバージョンを、可能な限り唯一の情報源として利用すること。

以下のバージョンが不整合にならないようにする。

* Rustパッケージ
* Windows実行ファイル
* インストーラー
* 生成物ファイル名
* 将来のGitタグまたはGitHub Release

バージョンを複数ファイルへ手動で重複記述する設計は、合理的な理由がない限り避ける。

## 権限と安全性

* workflowの権限は必要最小限とする
* Releaseを作成しない場合はcontentsへの書き込み権限を付与しない
* 外部Actionは信頼性、保守状況、権限を確認して選択する
* 不要なSecretsを追加しない
* コード署名用証明書は使用しない
* 生成物へ機密情報を含めない

# 9. CI

配布用workflowとは別に、通常のコード変更を検証するCIが既に存在するか確認すること。

存在しない場合、必要性を評価したうえで、最低限のWindowsビルド検証を追加する。

CIと配布物生成は、責務と実行頻度が異なるため、原則として分離する。

CIで実行するコマンドは、現在のコード品質、テスト状況、警告数を確認して決定すること。

既存コードに大量の警告がある状態で、無条件にすべての警告をエラー化して開発を停止させないこと。

# 12. 検証項目

実装後、可能な範囲で実際のWindows環境またはGitHub Actions上で検証すること。

## 実行ファイル

* Releaseビルドに成功する
* 起動時にコンソールウィンドウが表示されない
* アイコンとバージョン情報が設定されている
* 引数なしで起動できる
* PDFパスを指定して起動できる

## 単一インスタンス

* 未起動時に正常起動する
* 起動済みの場合は既存ウィンドウへタブ追加される
* 複数PDFを連続して開ける
* 同時起動要求でファイルが失われない
* 異常なパスでも受信処理全体が停止しない

## インストーラー

* 管理者権限なしでインストールできる
* スタートメニューから起動できる
* デスクトップショートカットの選択が反映される
* PDFを開くアプリとして表示される
* 既定アプリとして手動選択できる
* 上書きインストールできる
* アンインストールできる
* 他のPDFアプリの設定を破壊しない

## ポータブル版

* ZIPを展開して起動できる
* 不足ファイルがない
* 任意のフォルダから起動できる
* PDFを引数として開ける
* インストーラー版と基本機能に差がない
* レジストリ登録を行わない

## GitHub Actions

* 手動実行できる
* Releaseビルドに成功する
* インストーラーを生成できる
* ポータブルZIPを生成できる
* Artifactから両方を取得できる
* Artifact内のファイル名とバージョンが正しい
* 不要なファイルを含んでいない

実機で確認できない事項は、実施済みとして扱わず、未検証事項として明記すること。

# 13. 完了条件

以下をすべて満たした場合に完了とする。

1. Windows向けRelease実行ファイルが生成できる
2. 実行ファイルに適切なアイコンと製品情報が設定されている
3. PDFファイルをコマンドライン経由で正常に開ける
4. 起動済みLunaPDFへPDFを新しいタブとして渡せる
5. 管理者権限不要のインストーラーを生成できる
6. Windows上でPDF対応アプリとして登録できる
7. ユーザーがLunaPDFを既定のPDFアプリとして選択できる
8. インストール不要のポータブルZIPを生成できる
9. GitHub Actionsの手動実行で両配布物を生成できる
10. 生成物をArtifactから取得できる
11. ビルドおよび利用手順が文書化されている
12. 既存のタブ、分割ビュー、PDF表示、注釈、セッション機能に明確な回帰がない
