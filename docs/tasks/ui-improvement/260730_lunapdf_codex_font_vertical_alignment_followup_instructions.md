# Codex向け LunaPDF UI文字縦位置・フォントメトリクス追補修正指示書

## 1．目的

LunaPDFのツールバー、タブ、サイドバーの一覧などで、文字が確保された領域の上下中央よりもわずかに上へ寄って見える問題を修正してください。

本件は、直前のUI中央揃え修正を実装した後に残った視覚上の問題です。既存の中央揃え処理を作り直す全面改修ではありません。

作業開始時点の最新`main`を基準とし、フォントメトリクスと実際の字面の視覚中心の差を補正する、必要最小限の追補修正として対応してください。

## 4．現象

次のUIで、文字が領域の幾何学的な上下中央よりも少し上へ寄って見えます。

* ツールバーの通常ラベル
* ページ番号、総ページ数、ズーム倍率、検索件数
* ページ番号入力欄
* 検索入力欄
* タブタイトル
* ハイライト一覧のページ番号とコメント
* アウトラインなどの通常リスト項目
* その他、同じProportionalフォントを使用するUI

文字列が日本語のみの場合と、日本語と半角英数字が混在する場合の両方を確認してください。

## 5．現在の実装を維持する

現行コードでは、少なくとも次の幾何学的中央揃えが既に導入されています。

* ツールバーは固定高の行内で中央揃えされている。
* タブタイトルは、タイトル用矩形とgalleyの高さから中央位置を計算している。
* ハイライト一覧も、行矩形とgalleyの高さから中央位置を計算している。
* 色スウォッチは行矩形の中央へ配置されている。

これらを、原因確認なしに別のレイアウト方式へ置き換えないでください。

次のような処理が既に正しく機能している場合は維持してください。

```text
text_rect.center().y - galley.size().y / 2
```

矩形上の中央揃えが正しいにもかかわらず字面が上寄りに見える場合、問題はレイアウト矩形ではなく、フォントのascender、descender、line gap、グリフ形状などによる視覚中心の差として扱ってください。

## 6．原因確認

修正前に、少なくともWindows実機で次を確認してください。

1. 実際に選択されているフォントファイル。
2. 游ゴシック、メイリオなど、どの候補が読み込まれているか。
3. 日本語と半角英数字が同じフォントで描画されているか。
4. galley矩形の中央と、文字の実際の描画位置。
5. タブ、ハイライト一覧、ツールバーでずれの方向と量が概ね共通か。
6. TextEditだけに追加の内部余白または縦揃え差が存在するか。
7. 表示倍率によってずれが大きく変化するか。

必要ならデバッグビルド限定で次を一時表示してください。

* ウィジェット矩形
* テキスト用矩形
* galley矩形
* 各矩形の中心線
* 使用フォント名
* 適用したフォント補正値

通常ビルドへ診断表示を残さないでください。

原因を確認できなかった場合は、確定原因として報告せず、「推定」または「未確認」と明記してください。

## 7．必須修正

### 7.1 フォント登録時に補正する

矩形上の中央揃えが正しく、複数のUIで同じ方向へずれていることを確認できた場合は、各UI要素ではなく、UIフォントの登録時に描画位置を補正してください。

使用中の`egui`バージョンで利用可能なフォント調整APIを確認し、`FontData`または同等のフォント設定に対して、Y方向の描画オフセットを設定してください。

実装候補は次です。

* `FontTweak`
* `FontData::tweak`
* 現行バージョンに存在する同等のAPI

API名や正負方向は推測せず、`egui 0.35`の実コードまたは公式APIを確認してください。

初期検証値は、文字を下方向へ約`1.0 logical point`移動する値を目安としてください。

ただし、`1.0`を無条件に確定値とせず、次を比較して最終値を決めてください。

* 補正なし
* 約`0.5 logical point`
* 約`1.0 logical point`
* 必要な場合のみ約`1.5 logical point`

最小限の補正で、ツールバー、タブ、一覧のすべてが自然に見える値を採用してください。

### 7.2 フォント候補ごとの差を考慮する

Windowsでは游ゴシックとメイリオでメトリクスが異なる可能性があります。

読み込んだフォントに関係なく、同じ補正値を無条件に適用してよいとは限りません。

実機確認の結果、候補ごとに必要な補正が異なる場合は、既存のフォント候補定義へ最小限の補正情報を関連付けてください。

実装例としては、次のような簡潔な構造を優先してください。

```text
フォント候補のパスまたはファイル名
対応するY方向補正値
```

このためだけに不要な状態管理型、巨大な設定型、実行時設定画面を追加しないでください。

単純なタプル、定数、または小さなヘルパーで責務を表現できる場合は、それを優先してください。

### 7.3 OSごとに影響範囲を限定する

Windows実機だけで現象を確認できた場合は、Windows用フォントだけへ補正を適用してください。

LinuxおよびmacOSへ、検証していない補正を一律に適用しないでください。

他OSで同じ現象を確認できた場合は、OSおよびフォント候補ごとに結果を記録し、必要な範囲だけ補正してください。

### 7.4 Proportionalフォントを中心に修正する

今回の対象は通常UIです。

* メニュー
* ラベル
* ボタン
* タブ
* リスト
* ツールチップ
* 通常の入力欄

PDF本文のフォント処理は変更しないでください。

`Monospace`へ同じ補正を適用する必要性が確認できない場合は、変更しないでください。

### 7.5 TextEditの縦揃えを確認する

ページ番号入力欄と検索欄は、通常ラベルとは異なり、TextEdit固有の内部レイアウトを使用します。

使用中の`egui`バージョンに明示的な縦揃え設定が存在する場合は、その挙動を確認してください。

TextEditだけがフォント補正後も上寄りまたは下寄りになる場合は、TextEdit自身の垂直中央揃えを明示してください。

ただし、フォント補正とTextEdit固有補正が二重に適用されないようにしてください。

TextEdit内部へ直接固定Y座標を加える実装は避けてください。

## 8．禁止事項

次の修正は行わないでください。

* タブタイトルだけへ`+1.0`などのY座標を加える。
* ハイライト一覧だけへ固定Yオフセットを加える。
* ツールバーの各ラベルを個別に下げる。
* ウィジェットごとに異なる根拠のない補正値を設定する。
* 問題を隠すためにタブやツールバーの高さを大きくする。
* 現在のコンパクトなツールバー高さを元へ戻す。
* クリック領域を小さくする。
* 半角英数字を全角へ変換する。
* フォントファイルをリポジトリへ追加する。
* PDF本文のフォントやレンダリング処理を変更する。
* 新しい外部依存関係を追加する。
* ユーザー向けのフォント位置調整設定を追加する。
* 本件と無関係なUIリファクタリングを行う。
* commit、push、PR作成を行う。

## 10．自動テスト

GUIの見かけ上の中心位置を完全に自動判定できない場合も、補正ロジックを検証可能な単位へ分けてください。

少なくとも次を追加または更新してください。

### 10.1 フォント候補

* フォント候補パスが重複していない。
* 既存のOS別候補を維持している。
* 補正値が意図したフォント候補へ対応する。
* フォントが存在しない場合、次候補へ進む。
* フォントが一つも見つからない場合も起動を妨げない。

### 10.2 補正範囲

* Windows用補正が、検証していないOSへ適用されない。
* ProportionalとMonospaceの扱いが意図どおりである。
* 補正を複数回適用しない。
* 同じフォントデータを異なる経路で二重登録しない。

### 10.3 レイアウト回帰

既存テストで次を維持してください。

* タブタイトル領域と閉じる領域が重ならない。
* タブタイトル用矩形の中央がタブ矩形の中央と一致する。
* ハイライト一覧の文字領域と色スウォッチの中心が行中央と一致する。
* 行全体のResponse所有関係が変わらない。

光学的な字面位置は、無理に脆弱なピクセル完全一致テストへしないでください。
