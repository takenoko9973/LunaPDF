# LunaPDF 検索欄の操作性改善・検索再実行最適化 指示書

## 目的

PDF 内検索について、以下の3点を改善する。

1. 検索欄で Enter を押したとき、次の一致箇所へ順番に移動できるようにする。
2. 検索文字列が存在するとき、**検索入力欄の右端・入力欄内**に × ボタンを表示し、検索を即座にクリアできるようにする。
3. 検索文字列を保持した状態で PDF をスクロールすると検索処理が繰り返される問題を修正し、不要な検索処理を削減する。

既存の検索処理、検索結果表示、Split View、タブ管理、PDF 描画等を壊さず、必要最小限の変更で対応すること。

---

# 1. Enter による検索結果移動の不具合修正

## 現状

現在のコードには、検索欄にフォーカスがある状態で Enter を検出し、

- Enter → 次の検索結果
- Shift + Enter → 前の検索結果

へ移動する意図の実装が存在する。

概ね以下の経路になっている。

```text
検索欄 TextEdit
    ↓
Enter 検出
    ↓
search_navigation
    ↓
navigate_search()
    ↓
next_search_match()
    ↓
jump_to_search_match()
```

`next_search_match()` 自体には、

- 同一ページ内の複数一致
- ページを跨いだ検索結果
- 最後から最初への折り返し
- Shift+Enter による逆方向移動

のロジックが既に存在する。

しかし、実際の UI 操作では Enter を押しても検索結果へ遷移しない。

したがって、単純に Enter 用コードを追加するのではなく、**現在の入力イベント処理が実際に `navigate_search()` まで到達しているかを確認し、既存実装が動作しない原因を特定して修正すること。**

## 調査対象

少なくとも以下を確認する。

- `TextEdit` が Enter を先に消費していないか。
- `response.has_focus()` が Enter 処理時点で期待通り true になっているか。
- `response.changed()` と Enter が同一フレームで発生した場合の現在の条件が正しいか。
- IME、日本語入力確定時の Enter と通常の Enter を適切に区別できているか。
- `handle_shortcuts()` 等の別の入力処理が Enter を先に消費していないか。
- `search_navigation` が設定された後、`navigate_search()` が実際に呼ばれているか。
- `search.pages` に結果が存在していても `selected` が別処理によってリセットされていないか。
- `navigate_search()` 後の `restore_anchor` / `scroll_to_page` / `restore_single_anchor` が次フレームで上書きされていないか。

推測で修正せず、実際の原因を確認すること。

## 期待動作

検索結果が存在する場合、

```text
Enter
→ 現在位置以降の最初の一致
→ 次の一致
→ 次の一致
...
→ 最後の一致
→ 最初の一致へ折り返し
```

となること。

Shift + Enter は逆方向に同様に動作すること。

検索結果が0件の場合は何も移動しないこと。

検索処理がまだ進行中の場合でも、既に取得済みの検索結果については可能な範囲で遷移できる現在の設計を維持すること。

IME の文字確定操作を検索結果移動として誤認しないこと。

# 2. 検索欄のクリアボタン追加

## 要件

検索文字列が存在する場合のみ、**検索入力欄の右端・入力欄内部**に × ボタンを表示する。

概念的には以下の配置とする。

```text
[ 検索文字列                         × ]
```

× は検索欄の外側に独立したツールバーボタンとして配置しないこと。

検索文字列が空の場合は × を表示しない。

× をクリックした場合は、

```text
search.query.clear()
cancel_search(...)
```

相当の処理を行い、

- 検索文字列
- 検索結果
- 選択中検索結果
- 検索進捗
- 検索ハイライト

をクリアすること。

## UI

× は `TextEdit` の右端にオーバーレイまたは同等の方法で配置し、**入力欄の一部として見えること**。

検索文字列が長い場合でも、文字が × の下まで入り込まないよう、入力可能領域または右側余白を確保すること。

× の表示によって、

- 検索欄全体の外形サイズ
- ツールバーの高さ
- 検索欄以降の UI の位置

が変化しないこと。

つまり、× の表示・非表示によってツールバーが左右に動かないこと。

現在タブで使用している × 表示はベクター描画されているため、必要であればその描画処理を最小限再利用または共通化してよい。

ただし、

- 新しい画像アセットを安易に追加しない。
- × ボタンだけのために大きな UI 抽象化を追加しない。
- ツールバー全体の高さを変更しない。
- 現在の検索欄の垂直位置や文字配置を崩さない。
- × のクリック判定が検索欄全体へ広がらないようにする。
- × 以外の領域をクリックした場合は通常どおり TextEdit にフォーカスできるようにする。

こと。

# 3. スクロール時に検索が再実行される問題の修正

## 確認済みの問題

現在のコードでは、検索文字列がある状態で PDF 上をホイールスクロールすると、以下の経路を通る可能性がある。

```text
MouseWheel
    ↓
pointer_navigation
    ↓
pointer_side
    ↓
focus_side()
    ↓
TabState::select_tab()
    ↓
activate_document()
    ↓
begin_search()
```

`TabState::select_tab()` は、すでに同じタブが選択されている場合でも成功扱いとなる。

その結果、同じペインを通常スクロールしただけでも `activate_document()` が呼ばれる。

さらに現在の `activate_document()` には、

```rust
if !search.query.trim().is_empty()
    && !search.in_progress
{
    begin_search(...)
}
```

相当の条件が存在する。

検索完了後は `in_progress == false` なので、

```text
検索文字列あり
+
検索完了済み
+
ホイール操作
```

によって `begin_search()` が再度実行される。

`begin_search()` は既存結果を再利用する処理ではなく、

- `search.pages.clear()`
- `search.selected = None`
- `completed_pages = 0`
- generation 更新
- 全ページ分の `SearchPage` 再投入

を行う。

したがって、この再検索は単なる UI 更新ではなく、実際に MuPDF のページ検索を再度実行する不要な処理である。

---

# 4. 再検索を行う条件の整理

検索結果が現在の検索文字列・文書 revision に対して既に完成している場合、スクロールやフォーカス操作だけを理由に再検索してはならない。

一方、以下では検索再開または再検索が必要になる。

- 検索文字列が変更された。
- PDF の revision が変更された。
- 外部更新によって文書が再読み込みされた。
- 検索途中にタブまたはペインが非表示となり、検索がキャンセルされた。
- suspend → resume により worker が再生成され、検索処理の継続が必要になった。

この違いを明確にして実装すること。

---

# 5. 推奨する修正方針

## 5.1 同じペインへの不要な再 activation を避ける

`focus_side()` では、対象ペインのタブが既に active なら `activate_document()` を繰り返さないようにすることを検討する。

Split View では、

- 反対側ペイン上で最初にホイール操作
  → そのペインを active にする
- その後同じペイン上で連続スクロール
  → 再 activation しない

という動作にする。

ただし、現在 `activate_document()` が検索以外にも担っている責務を確認し、同一タブに対する呼び出しを省略しても問題ないことを確認してから変更すること。

単純に return を追加するだけで他機能を壊さないか検証する。

## 5.2 `activate_document()` の検索条件を修正する

現在の、

```text
query が空でない
&& !in_progress
```

だけでは検索完了済みと検索未実行・中断済みを区別できない。

例えば検索完了状態を、

```text
completed_pages >= page_count
```

で判断できるのであれば、それを利用する。

重要なのは **0件検索** である。

検索結果が0件の場合、

```text
search.pages.is_empty() == true
```

になるため、

```text
pages.is_empty()
```

を検索未実行判定として使用してはならない。

0件でも全ページ処理済みなら検索は正常完了している。

したがって、

```text
query が存在する
&& !in_progress
&& 検索が未完了
```

の場合のみ再検索する方向を基本とする。

ただし、現在の suspend / resume、外部更新、タブ非表示時キャンセルとの整合性を確認したうえで最終条件を決めること。

---

# 6. 検索状態の不必要な再構築を避ける

同一の、

```text
document revision
search query
```

に対する検索結果が完成している場合は、

- `generation` を更新しない。
- `pages` をクリアしない。
- `selected` をリセットしない。
- `SearchPage` を再投入しない。

こと。

Enter によるナビゲーション中にスクロールしても、現在選択している検索結果が失われないようにする。

これは Enter 不具合とも関連するため、両方を一体として確認すること。

---

# 7. バックエンド検索の追加キャッシュについて

今回の問題を解決するためだけに、

- 検索結果専用 LRU
- TextPage 全ページキャッシュ
- query hash cache
- 新しい非同期検索管理層

等を追加しないこと。

まず UI / 状態遷移上の不要な `begin_search()` を止める。

現状ではページ単位の検索は background queue に配置され、可視レンダリングより低い優先度で処理される設計になっている。

この既存設計を維持する。

---

# 8. テスト

既存テストを維持したうえで、最低限以下の回帰テストを追加する。

## Enter

- 検索結果が3件ある状態で Enter を繰り返すと、

```text
1 → 2 → 3 → 1
```

となる。

- Shift + Enter では逆方向へ移動する。
- 同一ページ内に複数一致があっても1件ずつ移動する。
- 異なるページ間でも移動する。
- 検索結果0件では移動しない。
- Enter によって検索そのものが再開始されない。
- IME 確定 Enter を検索結果移動として処理しない。

既存の `next_search_match()` 単体テストだけでは不十分である。

**実際の検索欄入力 → Enter → `navigate_search()` 相当の UI 経路もテストすること。**

## スクロール

検索完了状態を作り、その後 MouseWheel を入力する。

以下が変化しないことを確認する。

```text
search.generation
search.completed_pages
search.pages
search.selected
```

特に、

```text
検索完了
→ ホイール
→ generation が増えない
```

ことを回帰テストで保証する。

## 0件検索

```text
query != empty
completed_pages == page_count
pages.is_empty()
in_progress == false
```

という正常な0件検索完了状態を作る。

その後、

- スクロール
- 同じペインのフォーカス処理
- 通常の UI 再描画

を行っても検索が再開始されないこと。

## 中断された検索

```text
completed_pages < page_count
in_progress == false
```

となる中断状態では、再 activation 後に必要なら検索が再開されること。

## クリアボタン

検索文字列が存在するときだけ、入力欄右端内部に × が表示されること。

× をクリックした後に、

```text
query == ""
pages.is_empty()
selected == None
completed_pages == 0
in_progress == false
```

となること。

また、

- × を押しても検索欄の外形サイズが変わらない。
- × 以外の入力欄領域をクリックすると通常どおり TextEdit が操作できる。
- 長い検索文字列が × と重ならない。
- 古い generation の検索結果イベントが後から到着しても復活しない。

ことを確認する。

# 9. 手動確認

以下を実際のアプリで確認する。

1. PDFを開く。
2. 複数箇所に存在する文字列を検索する。
3. 検索完了を待つ。
4. Enter を数回押す。
5. 各一致箇所へ順番に移動することを確認する。
6. 最後から最初へ折り返すことを確認する。
7. Shift + Enter で逆方向へ移動する。
8. 検索文字列があるとき、入力欄右端内部に × が表示されることを確認する。
9. 長い文字列を入力しても、文字が × と重ならないことを確認する。
10. 検索文字列を残したままホイールを連続操作する。
11. 検索件数表示や進捗がリセットされないことを確認する。
12. スクロールしても選択中検索結果が失われないことを確認する。
13. × を押す。
14. 検索文字列と検索ハイライトが即座に消えることを確認する。
15. × が消えても検索欄や後続 UI の位置が変化しないことを確認する。
16. Split View でも左右それぞれをスクロールし、ペイン切替時以外に検索が再実行されないことを確認する。
17. 検索結果0件の語でもスクロールによる再検索が発生しないことを確認する。

可能であれば debug diagnostics 等を利用し、ホイール操作によって `SearchPage` が新規投入されていないことも確認する。

# 10. 変更範囲

主な調査・変更候補は以下。

```text
src/app.rs
src/app/search.rs
src/app/tests.rs
src/domain/tabs.rs
```

必要であれば既存の × 描画 helper 周辺を変更してよい。

ただし `src/pdf/worker.rs` や `src/pdf/mupdf_backend.rs` は、今回の原因が UI / 状態管理側にある限り変更しないこと。

バックエンド検索方式そのものを変更する必要はない。

# 11. 制約

- 今回指定した検索関連以外の UI や機能を変更しない。
- 無関係なリファクタリングを行わない。
- 新しい検索アーキテクチャを導入しない。
- 不要なキャッシュ層を追加しない。
- PDF 描画、文字選択、コピー、Highlight、注釈、Undo、印刷、タブ、Split View を壊さない。
- 現在の検索結果描画方式を維持する。
- 現在の background search priority を維持する。
- 既存の generation / revision による stale result 排除を維持する。
- 検索結果0件を「未検索」と誤認しない。
- Enter の問題を「既存コードがあるから正常」と判断せず、実際の UI 経路で再現・原因確認する。
- 原因不明のまま Enter 用の別ショートカット処理を重複実装しない。
- × ボタンを検索欄の外側に配置しない。
- × ボタン表示のために検索欄自体の幅やツールバー配置を動かさない。
- 最小差分を優先する。

# 完了条件

以下をすべて満たした時点で完了とする。

- 検索欄で Enter を押すと次の一致箇所へ移動する。
- Shift + Enter で前の一致箇所へ移動する。
- 最後・最初で正しく折り返す。
- IME 確定操作を壊さない。
- 検索文字列がある場合だけ、検索入力欄の右端内部に × が表示される。
- × が検索文字列と重ならない。
- × で検索状態を完全にクリアできる。
- × の表示・非表示で検索欄や後続 UI の位置が変化しない。
- 検索完了後の通常スクロールでは検索が再実行されない。
- 0件検索でも再検索されない。
- 検索途中で本当に再開が必要なケースでは再開できる。
- Split View のペインフォーカスが維持される。
- 検索結果選択が通常スクロールだけで失われない。
- stale search result の排除が維持される。
- 関連テストが追加され、既存テストも通る。
- 無関係な変更が含まれていない。
