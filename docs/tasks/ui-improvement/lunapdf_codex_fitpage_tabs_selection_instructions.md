# Codex向け LunaPDF 描画欠落・タブUI・テキスト選択修正指示書

## 目的

最新の`main`を基準に、次の3件を調査し、再現条件と原因を確認したうえで修正してください。

1. 「ページ全体表示」で横長PDFを表示すると、ページ右側が描画されない。
2. タブを一体型の外観へ変更し、タブ数に応じて最大幅から最小幅まで均等に縮小する。
3. テキスト範囲選択で、ドラッグ中のプレビューと確定後の選択範囲が一致しない。開始文字または終了文字が欠落する場合がある。

原因候補を先に固定しないでください。再現、計測、失敗テスト、修正後の再検証を順に行ってください。

## 対象

- リポジトリ：`takenoko9973/LunaPDF`

  - `src/app.rs`

  - `src/domain/selection.rs`
  - `src/pdf/mupdf_backend.rs`
  - `src/render/tiles.rs`
  - 関連するテストとテスト用PDF生成処理

上記は調査候補です。実際の責務はコードから確認してください。

# 3．横長PDFの右側が描画されない問題

## 3.1 現象

「ページ全体表示」でスライドなどの横長PDFを表示すると、ページ右側の一部または右半分が描画されない場合があります。

描画待ちによる一時的な白紙と、タイルが要求または描画されない恒久的な欠落を区別してください。

## 3.2 再現条件

ユーザーが確認したPDFを利用できる場合は、そのPDFを優先してください。

例として報告されているファイル名：

- `打合せ_0216.pdf`
- `260304_GaN.pdf`

利用できない場合は、既存のテスト用PDF生成方法を使い、横長ページを持つ最小PDFを生成してください。テスト専用の一時ファイルは作業後に残さないでください。回帰テストに必要な最小fixtureだけは、既存方針に従って追加して構いません。

次の条件を分けて確認してください。

- 単一ページ表示と連続表示。
- FitPage、FitWidth、固定ズーム。
- 1ページPDFと複数ページPDF。
- 横長、正方形、縦長ページ。
- 100%、125%、150%、200%相当の`pixels_per_point`。
- サイドバー開閉前後。
- ウィンドウサイズ変更前後。
- FitPage切替直後と、描画要求が完了した後。

## 3.3 計測項目

一つの再現ケースについて、次の値を同じフレームまたは同じ描画世代で対応づけて記録してください。

### レイアウト

- PDFページの`PageRect`。
- `ui.available_size()`。
- FitPage計算に使用した幅と高さ。
- 計算後のズーム値。
- ページの表示矩形。
- ScrollAreaのcontent size。
- ScrollAreaのvisible viewport。
- スクロールオフセット。
- eguiのclip rect。

### タイル要求

- `TileGrid`のpixel widthとpixel height。
- 可視領域から計算した要求範囲。
- 論理座標からpixel座標へ変換した境界。
- 生成された`TileSpec`の一覧または列・行の範囲。
- 最右列のタイルが要求されているか。
- `wanted_tiles`と`visible_tiles`。
- 要求後にキャンセルされたタイル。
- タイルのpriority。

### ワーカーとMuPDF

- ワーカーが受理した`TileRequest`。
- MuPDFへ渡すpage pixel bounds。
- `tile_clip()`の入力と出力。
- 返却された`RenderedTile.spec`。
- 返却された`page_pixel_width`と`page_pixel_height`。
- 最右列のタイルが正常に返却されたか。

### キャッシュと描画

- `tile_result_is_current()`の判定結果。
- GPU LRUへの挿入結果。
- `paint_page_tiles()`が列挙したタイルキー。
- `screen_rect_for_tile()`が生成した最右列の描画矩形。
- 最右列の描画矩形とページ右端の差。
- clip rectとの交差。
- 暫定タイルと正確なタイルの描画順。

## 3.4 原因判定

次のいずれの段階で最初に期待値から外れたかを示してください。

1. FitPageのズームまたはページ配置。
2. viewportまたはclip rect。
3. タイル要求範囲。
4. タイルのスケジューリングまたはキャンセル。
5. MuPDFのclipと返却座標。
6. タイルキーと世代の照合。
7. GPUキャッシュ。
8. 画面上のタイル矩形。

修正対象は、最初に不整合が発生した処理を基本としてください。

FitPage時に現在ページの全タイルを要求する方式を採用する場合は、可視範囲計算の修正だけでは解決できない理由を示してください。巨大ページ、拡大表示、メモリ使用量、先読みとの整合性も検証してください。

## 3.5 回帰テスト

少なくとも次を追加してください。

- 横長ページのFitPageで、要求範囲がページ右端まで達する。
- 最右列の`TileSpec`が必要な条件で生成される。
- 最右列の画面矩形右端がページ矩形右端と一致する。
- 非整数DPIで右端が欠落しない。
- ページ原点が`(0, 0)`でなくても右端まで描画される。
- 縦長ページと正方形ページを壊さない。
- 拡大表示で不要な全ページタイルを要求しない。
- ウィンドウサイズ変更後に再計算される。

# 4．一体型タブと動的なタブ幅

## 4.1 目標

現在のタイトル部分、閉じるボタン、区切りを別々に並べる外観を廃止し、一つのタブ矩形の内部にタイトルと閉じる領域を配置してください。

目標イメージ：

```text
┌──────────────────────┐
│ ファイル名…        × │
└──────────────────────┘
```

閉じる操作は残してください。

## 4.2 タブ幅

タブ数が増えるにつれて、全タブを同じ幅で縮小してください。

次の規則を満たしてください。

- 1個または少数のタブは最大幅を超えて広がらない。
- タブ数が増えると、利用可能幅に収まる範囲で均等に縮小する。
- 最小幅へ到達するまでは横スクロールを発生させない。
- 最小幅へ到達した後は、それ以上縮小せず横スクロールを使用する。
- 選択中タブが横スクロール範囲外へ隠れた場合は、選択時に表示範囲へ移動する。
- 閉じる領域の幅はタブ縮小後も維持する。
- タイトル領域が閉じる領域へ重ならない。

幅計算をUI描画から分離し、単体テストできる関数にしてください。

概念上は次の値を使いますが、実際のegui spacingとpaddingを含めて計算してください。

```text
均等幅 = タブバーの利用可能幅 ÷ タブ数
タブ幅 = 均等幅を最小幅と最大幅の範囲へ制限
```

最大幅と最小幅は、実画面で確認して決めてください。既存の見た目と操作性を基準とし、値を推測だけで決めないでください。採用値と確認方法を報告してください。

## 4.3 タブ内部

一つのタブ矩形を確保し、その内部を少なくとも次の領域へ分けてください。

- タブ選択領域。
- dirtyマーカー。
- 省略可能なタイトル。
- 閉じる領域。

要件：

- タイトル部分をクリックするとタブを選択する。
- 閉じる領域をクリックしてもタブ選択を発火させない。
- 閉じる領域に独立した常時枠を表示しない。
- 閉じられない状態では、現在の無効化条件を維持する。
- タイトルが収まらない場合は省略表示する。
- ホバーで完全なファイル名またはパスを表示する。
- 日本語、ASCII、長いファイル名、dirtyマーカーで崩れない。
- 選択中と非選択中を判別できる。
- ライトテーマとダークテーマで判別できる。
- タブ間の`separator`による独立感を残さない。
- タブ下辺と表示領域の境界を二重線にしない。

## 4.4 検証

ロジックテスト：

- 0タブでゼロ除算しない。
- 1タブが最大幅を超えない。
- タブ数増加に従い幅が単調に縮小する。
- 最小幅へ到達するまでは総幅が利用可能幅を超えない。
- 最小幅到達後は幅が固定される。
- タブ間隔を含めた総幅が正しい。
- タイトル領域と閉じる領域が重ならない。

手動確認：

- 1、2、5、10、20タブ。
- 狭いウィンドウと広いウィンドウ。
- 日本語名。
- 長い英数字名。
- 同名ファイル。
- dirtyタブ。
- 印刷中など閉じられないタブ。
- 最小幅到達後の横スクロール。
- 選択中タブの自動表示。

# 5．テキスト選択のプレビューと確定結果の不一致

## 5.1 現象

次の不一致が報告されています。

- ドラッグ開始時に指した最初の文字が、確定後に含まれない。
- ドラッグ終了時に指した最後の文字が、確定後に含まれない。
- ドラッグ中のプレビューと、ボタンを離した後の選択範囲が異なる。
- コピー文字列、確定表示、ハイライト注釈の対象範囲が一致しない可能性がある。

どの処理が不一致を生んでいるかを計測してください。プレビューと確定処理が異なることだけを根拠に、原因を確定しないでください。

## 5.2 再現条件

最低限、次を確認してください。

- 1文字だけ。
- 行頭から行末。
- 行の途中から途中。
- 左から右。
- 右から左。
- 上から下。
- 下から上。
- 複数行。
- 行頭文字を開始点にする。
- 行末文字を終了点にする。
- 文字の左端、中央、右端付近から開始する。
- 文字の外側で終了する。
- FitPage、FitWidth、固定ズーム。
- 100%、125%、150%、200%相当のDPI。
- ページ原点が非ゼロのPDF。
- Typstで生成したPDFと、別の一般的なPDF。

## 5.3 計測項目

一回のドラッグ操作について、次を同一のselection generationで記録してください。

- 生のpointer座標。
- PDF座標へ変換した開始点と終了点。
- 開始時に選ばれたglyph indexと文字。
- 終了時に選ばれたglyph indexと文字。
- ドラッグ方向。
- プレビューが使用したglyph範囲。
- プレビューで描画したQuad。
- ワーカーへ送信した値。
- ワーカー側が使用した選択境界。
- 確定後の文字列。
- 確定後のQuad。
- ハイライト作成へ渡されるQuad。
- プレビューと確定結果の差分。

ログには文書パス全体を不要に出さず、ページ番号、generation、index、座標を中心に記録してください。

## 5.4 整合性

最終的に次の4つが同じ論理範囲を表す必要があります。

1. ドラッグ中のプレビュー。
2. ドラッグ確定後の画面表示。
3. `Ctrl+C`でコピーされる文字列。
4. ハイライト注釈へ渡されるQuad。

不一致がある場合は、どの段階で別の範囲へ変換されたかを特定してください。

## 5.5 修正方法の選定

調査結果に基づき、論理選択範囲を一つに統一してください。

実装候補として次がありますが、調査前に固定しないでください。

### glyph indexを正とする場合

- pointerから開始indexと終了indexを決定する。
- 両端を含む範囲を論理選択として保持する。
- プレビュー、文字列、確定表示、ハイライトQuadを同じ範囲から生成する。
- 同一行の連続glyphを結合する場合も、単一の共通関数を使用する。

### PDF上の境界点を正とする場合

- 文字中心ではなく、開始側と終了側を表す境界点を構築する。
- ドラッグ方向を考慮する。
- MuPDFの結果がプレビュー、コピー、ハイライトと一致することをテストする。

### MuPDF結果を操作中にも使用する場合

- 操作中の応答時間を計測する。
- 遅延やワーカー競合がないことを確認する。
- 古い結果が新しいドラッグへ適用されないようgenerationを照合する。

固定座標オフセットや、端文字だけを無条件に追加する処理で不一致を隠さないでください。

## 5.6 Quad生成

glyphからQuadを生成または結合する場合は、次を満たしてください。

- 開始文字と終了文字を欠落させない。
- 行をまたいで誤結合しない。
- コピー順を変更しない。
- 回転または傾斜したQuadを、不必要に水平矩形へ変換しない。
- Typst PDFで選択範囲が過度に広がる問題を再発させない。
- PDF Highlight注釈が要求するQuad順序を維持する。
- 選択プレビューと確定表示で同じQuad生成処理を使用する。

## 5.7 非同期処理

次を確認してください。

- 古いselection generationの結果が新しい選択を上書きしない。
- タブ切替後の結果が別タブへ適用されない。
- 文書revision変更後の古い結果が使われない。
- 選択中にズームまたは表示モードを変えた場合に状態が破綻しない。
- テキストsnapshotと確定選択が同じrevisionを参照する。

不足が確認された場合だけgenerationまたはrevision管理を修正してください。

## 5.8 回帰テスト

少なくとも次を追加してください。

- 1文字選択で対象文字を含む。
- 行頭文字を開始点にして欠落しない。
- 行末文字を終了点にして欠落しない。
- 逆方向ドラッグでも同じ論理範囲になる。
- 複数行で各行の端を欠落しない。
- プレビューと確定後のQuadが一致する。
- コピー文字列のglyph範囲と表示Quadの対象が一致する。
- ハイライトへ渡すQuadが確定表示Quadと一致する。
- 文字外側で終了した場合の規則が一貫する。
- 非ゼロページ原点で動作する。
- Typst PDF用の既存選択精度を悪化させない。
