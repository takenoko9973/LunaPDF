# Codex向け LunaPDF 閉じた手カーソル資産化・CUR統合 指示書

## 1．目的

LunaPDFのPDF表示領域でパン操作が成立した際に表示する「閉じた手」カーソルを、現在の実行時生成方式から、複数解像度を内包する単一のWindowsカーソルファイルへ置き換えてください。

現在のカーソルは、Rustコード内に輪郭点と内部線を定義し、実行時にスーパーサンプリングしてRGBA画像を生成しています。機能上はパン中のカーソルとして動作していますが、形状に手作り感があり、一般的なデスクトップアプリで見慣れた閉じた手カーソルに見えません。

今回の変更では、古典的な白黒の`closed-hand`カーソル、特に旧Web地図で広く使われた簡潔な形状へ視覚的に近づけたLunaPDF独自資産を作成し、単一の`.cur`ファイルとして管理してください。

元となる第三者の`.cur`ファイル、Base64データ、ピクセルマップ、輪郭座標は使用しないでください。見た目の方向性は近づけますが、資産は新規作成してください。

# 6．カーソルの視覚仕様

## 6.1 基本方針

LunaPDF用の閉じた手カーソルを新規作成してください。

目標は、古典的なWindowsアプリや旧Web地図で使われてきた、簡潔な白黒`closed-hand`カーソルに見えることです。

現在の写実的または不規則な手の形ではなく、小さい表示でも即座に「掴んでいる手」と認識できる記号的な形状にしてください。

## 6.2 必須の形状

- 白塗り。
- 黒い輪郭。
- 32px表示で輪郭が明瞭に見える。
- 上側に折り曲げた指の並びが見える。
- 掌と親指の関係が判別できる。
- 指の数を細かく描き込みすぎない。
- 手首を長くしすぎない。
- 掌を縦長にしすぎない。
- 内部線を必要最小限にする。
- 1-bitカーソルに近い簡潔な印象を保つ。
- アンチエイリアスで輪郭を過度にぼかさない。
- 白背景、PDFの白地、灰色背景、ダーク背景で認識できる。

## 6.3 視覚参照への近づけ方

ユーザーが意図する参照形状は、旧Google Mapsなどで広く見られた古典的な`closedhand`カーソルです。

次の特徴は近づけて構いません。

- 小さくまとまった握り拳。
- 白い面と黒い輪郭。
- 上部へ並ぶ折り曲げた指。
- 掌の前または側面へ回り込む親指。
- 32pxで読み取れる単純なピクセル表現。
- 古いWindowsカーソルに近いシャープな印象。

ただし、次は禁止します。

- 元の`.cur`ファイルを取得して含める。
- 元ファイルのBase64を含める。
- 元画像を自動変換して出力する。
- ピクセルマップをコピーする。
- 元画像を下敷きにして輪郭をトレースする。
- 数ピクセル移動、拡大縮小、色変更だけで別資産とする。
- 第三者のホットスポット値をそのまま転記する。
- 第三者資産を「LunaPDF独自作成」と記載する。

輪郭、指幅、親指、掌、手首、内部線をLunaPDF用に新規設計してください。ただし、独自性を強調するために不自然な形へ崩さないでください。

## 6.4 サイズ別調整

32pxの原画を単純に拡大しただけで完了としないでください。

`.cur`内部には、少なくとも次のフレームを格納してください。

- 32×32
- 40×40
- 48×48
- 56×56
- 64×64

各フレームは同じ形状を基礎にしながら、必要に応じて次を微調整してください。

- 輪郭幅。
- 内部線幅。
- 指の隙間。
- 親指の判別性。
- 透明領域との境界。
- 小さいサイズで潰れる細部。

全フレームを別々の独立した絵として作らず、同じ原画と同じ比率を基準にしてください。

## 6.5 ホットスポット

ホットスポットは完成した形状を確認して決定してください。

次を満たしてください。

- 掴んでいる位置と操作点が直感的に一致する。
- パン開始時にカーソル画像が不自然に跳ねて見えない。
- DPIごとに相対位置が変わらない。
- 画像外または輪郭の端へ不自然に寄せない。
- 全フレームで正規化した位置をそろえる。

ホットスポットを「画像中央」と先に決め打ちしないでください。画像の掌または掴み位置を基準に、Windows実機で確認してください。

# 7．資産構成

## 7.1 基本構成

リポジトリでは、複数のPNGを実行用資産として個別管理せず、複数解像度を内包する単一の`.cur`ファイルを実行用資産としてください。

推奨構成：

```text
assets/
└─ cursors/
   ├─ grabbing.svg
   └─ grabbing.cur
```

- `grabbing.svg`：編集用の原本。
- `grabbing.cur`：複数解像度とホットスポットを含む実行用資産。

SVG以外の編集用形式が既存方針に適合する場合は変更して構いません。ただし、生成済み`.cur`だけを手作業で編集する運用にはしないでください。

## 7.2 `.cur`の要件

`grabbing.cur`は次を満たしてください。

- CUR形式として有効である。
- ディレクトリ種別がカーソルである。
- 必要な全解像度を一つのファイルへ格納する。
- 各フレームに有効なホットスポットを持つ。
- 透明背景を保持する。
- Windowsで読み込める。
- 同じ入力から同じバイナリを生成できる。
- 不要なメタデータや生成日時により毎回差分が出ない。
- 元の第三者カーソルデータを含まない。

内部画像をPNG圧縮またはDIBとして格納するかは、実際の読み込み経路とWindows互換性を確認して決定してください。

## 7.3 通常ビルドの要件

通常の次の操作で、外部の画像編集ソフトやネットワーク取得を要求しないでください。

```bash
cargo check
cargo test
cargo build
cargo build --release
```

生成済みの`grabbing.cur`はリポジトリへ含めてください。

カーソル資産を更新する場合だけ、明示的な生成手順を実行する構成としてください。通常ビルドのたびにSVGからCURを再生成する必要はありません。

# 9．LunaPDFへの統合

## 9.1 優先する統合方針

現在のegui／eframeによるカーソル決定経路を維持してください。

望ましい順序は次です。

1. `.cur`を資産の正とする。
2. 必要なフレームとホットスポットを、ビルド前または資産生成時にRGBAデータへ変換する。
3. 実行時は現在のDPIに対応するフレームを選ぶ。
4. `egui::CustomCursorImage`へRGBA、サイズ、ホットスポットを渡す。
5. `CursorIcon::Grabbing`の場合だけWindowsでカスタム画像を設定する。

現在のegui APIが`.cur`を直接扱える場合は、そのAPIを優先して構いません。ただし、使用中の`eframe = 0.35.0`と実際のバックエンドで動作することを確認してください。

## 9.2 Win32ネイティブ統合

`LoadImageW`、`HCURSOR`、`WM_SETCURSOR`などを直接扱う方式は、既存egui経路では要件を満たせないことを確認した場合だけ検討してください。

ネイティブ統合を採用する場合は、次を確認してください。

- eframeが同一フレームでカーソルを上書きしない。
- ウィンドウハンドルの取得が既存構成で安全に行える。
- `HCURSOR`の所有権と破棄方法が正しい。
- タブ、メニュー、TextEditなどPDF領域外へカーソルが漏れない。
- `WM_SETCURSOR`の処理が既存入力を壊さない。
- 非Windowsビルドへ影響しない。

今回の見た目変更だけを理由に、アプリ全体へ大規模なネイティブウィンドウ処理を追加しないでください。

## 9.3 DPI選択

現在の`pixels_per_point`から、CUR内の最適なフレームを選んでください。

最低限、次を適切に選択してください。

| `pixels_per_point`の目安 | 使用候補 |
|---:|---:|
| 1.00 | 32px |
| 1.25 | 40px |
| 1.50 | 48px |
| 1.75 | 56px |
| 2.00 | 64px |

中間値では最も近いフレームを選ぶか、Windowsまたは使用APIの標準選択を利用してください。

同じDPIで毎フレームデコードしないでください。必要なデータは一度だけ解析またはキャッシュしてください。

## 9.4 状態遷移

今回の変更ではカーソル画像だけを変更し、次の状態遷移を維持してください。

| 状態 | カーソル |
|---|---|
| 通常閲覧 | 通常矢印 |
| PDF本文の文字上 | Iビーム |
| リンク上 | 指差し |
| 注釈・画像・フォーム上 | 通常矢印 |
| 左ボタン押下後、パン閾値未満 | 通常矢印 |
| パン閾値を超えてパン成立 | 新しい閉じた手 |
| 左ボタン解放後 | 直下の対象に応じて即時復帰 |
| 中ボタン自動スクロール中 | 既存の自動スクロールカーソル |

パン中に文字上を通過しても、パンが成立している間は閉じた手を維持してください。

自動スクロール中に閉じた手へ切り替えないでください。

カーソル画像のために、既存のパン状態と別のboolや状態機械を追加しないでください。

# 12．自動テスト

## 12.1 CUR構造

生成処理または読み込み処理に対して、少なくとも次を検証してください。

- CUR形式として識別できる。
- カーソル種別である。
- 想定するフレーム数を持つ。
- 32、40、48、56、64pxを含む。
- 各フレームが正方形である。
- 各フレームのホットスポットが画像範囲内である。
- 各フレームに透明画素と不透明画素が存在する。
- フレームデータが重複または欠落していない。
- 生成結果が決定的である。

## 12.2 DPI選択

- 1.00で32pxを選ぶ。
- 1.25で40pxを選ぶ。
- 1.50で48pxを選ぶ。
- 1.75で56pxを選ぶ。
- 2.00で64pxを選ぶ。
- 中間値で意図した最寄りサイズを選ぶ。
- 異常な値でpanicしない。
- 上下限外は安全なサイズへクランプする。

## 12.3 カーソル状態

既存の状態テストを維持し、少なくとも次を確認してください。

- 通常時は`Default`。
- 文字上は`Text`。
- リンク上は`PointingHand`。
- パン閾値未満は`Default`。
- パン成立中は`Grabbing`。
- パン終了後は直下の対象へ戻る。
- 自動スクロール中は`AllScroll`。
- 自動スクロールとパン中が同時に成立しない。
- 非WindowsではカスタムCUR処理を要求しない。

## 12.4 埋め込み

- releaseビルドで資産が利用できる。
- 実行時にリポジトリの相対パスを開かない。
- カレントディレクトリに依存しない。
- 資産欠落を実行時まで見逃さない。
- 生成済み埋め込みデータがある場合、CURとの対応を検証できる。

画像の美観は自動テストだけで完了扱いにしないでください。
