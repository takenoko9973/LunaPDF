# Codex向け LunaPDF タブ並べ替え・左右分割ビュー実装指示書

## 1．目的

作業開始時点の最新`main`を基準に、LunaPDFへ次の機能を追加してください。

1. タブをドラッグして、同一タブ列内で表示順を変更できるようにする。
2. タブをPDF表示領域の指定位置へドラッグし、同一ウィンドウ内を左右2ペインへ分割できるようにする。
3. 分割後、タブを左右のペイン間で移動できるようにする。
4. 将来、上下分割へ拡張する場合に、タブ管理や文書状態を全面的に作り直さずに済む構造へ整理する。

初期実装で対応する分割方向は左右のみとします。

初期実装で同時に表示できるペイン数は最大2としてください。3ペイン以上、左右と上下を組み合わせたネスト分割、別ウィンドウへの切り離しは今回の対象外です。

本書では、具体的な型、コンテナ、モジュール構成、egui API、ドラッグ＆ドロップAPI、レイアウト表現、永続化形式を決め打ちしません。

最新コードの責務、既存の不変条件、非同期処理、使用中のegui／eframeのAPIを調査し、要件を満たす最小かつ保守可能な設計をCodex側で計画してください。

# 7．設計上の要求

## 7.1 安定したタブ同一性

タブの表示位置が変わっても、次の状態が別の文書へ移らないようにしてください。

* 文書ワーカー。
* PDF情報。
* ページ位置。
* ズーム状態。
* 検索状態。
* テキスト選択。
* 注釈キャッシュ。
* 編集履歴。
* dirty状態。
* 保存中状態。
* 印刷中状態。
* 描画タイル。
* サムネイル。
* エラー。
* セッション復元状態。

表示順のインデックスだけを長寿命の同一性として使用しないでください。

具体的なID型やコンテナは、現行コードを確認して選定してください。

## 7.2 タブ集合と文書集合の整合性

タブ情報と文書実体を別々の可変コレクションで保持する場合は、並べ替え、移動、終了、復元のすべてで整合性を保証できる根拠を示してください。

一つの所有構造へ統合するか、安定IDで関連付けるか、別の方式を採用するかは固定しません。

ただし、二つのコレクションを同じインデックスで暗黙に対応させたまま、個別に並べ替える実装は避けてください。

## 7.3 フォーカス中と表示中を区別する

分割後は、左右の文書が同時に表示されます。

次を明確に区別してください。

* フォーカス中のペイン。
* 各ペインで選択されているタブ。
* 現在画面へ表示されているタブ。
* 非表示のタブ。
* 閉じる確認または注釈編集の対象タブ。

フォーカスされていない側の表示タブを、単なる非アクティブタブとして描画対象外にしないでください。

一方、ショートカットや共通ツールバーの対象は、原則としてフォーカス中ペインの選択タブとしてください。

## 7.4 PDF操作状態の分離

左右の表示領域で、次の一時状態が混ざらないようにしてください。

* テキスト選択ドラッグ。
* 空白パン。
* 中ボタン自動スクロール。
* 右クリック対象。
* 注釈候補。
* 選択解除判定。
* ScrollAreaのスクロール状態。
* 単一ページ用ホイール状態。
* 表示領域固有の入力フォーカス。

現在のPDF操作状態をペインごとに所有するか、同等の分離を行ってください。

具体的な型分割はCodex側で決めてください。

## 7.5 将来の上下分割

今回実装する方向は左右のみです。

ただし、次のような左右専用構造へ固定しないでください。

* 左ペインと右ペインを固定フィールドとして持つ。
* X座標だけを前提にした分割状態。
* 左右専用のタブ移動APIしか持たない。
* セッション形式へ`left`と`right`だけを直接埋め込み、方向追加に全面移行を必要とする。
* 表示領域の高さ方向では再利用できない分割計算を、タブ管理と密結合する。

将来上下分割を追加する場合に、主として次の追加で対応できる設計を目指してください。

* 上下方向のドロップ領域。
* 高さ方向のレイアウト計算。
* 横向きセパレーター。
* ペイン最小高さの判定。
* 上下分割用の手動受入確認。

ただし、将来用途だけを理由に、未使用の複雑な分割木、汎用ドッキングフレームワーク、任意個ペイン管理、プラグイン機構を実装しないでください。

初期実装は最大2ペインです。

# 8．タブ並べ替え

## 8.1 必須操作

同一ペインのタブバー内で、タブをドラッグして表示順を変更できるようにしてください。

次を満たしてください。

* ドラッグ開始前の通常クリックは、従来どおりタブ選択として動作する。
* 小さなポインター移動だけで意図せず並べ替えを開始しない。
* 閉じる領域から並べ替えを開始しない。
* 中クリック終了を壊さない。
* ドラッグ中に挿入位置を識別できる。
* 左端、タブ間、右端へ移動できる。
* 移動後も同じ論理タブが選択状態を維持する。
* 非選択タブを移動した場合、不要に選択状態を変更しない。
* dirty状態、保存中、印刷中、エラー、休止中のタブも、既存の操作制約を守りながら正しい状態で移動できる。
* 多数タブと水平スクロールを壊さない。
* タブを移動しただけで文書を再オープンしない。
* タブを移動しただけで検索、ページ位置、ズーム、選択、Undo履歴を破棄しない。

タブドラッグ中の水平自動スクロールが必要かは、現行の多数タブ操作を確認して判断してください。

実装しない場合は、操作可能範囲と制約を作業報告へ記載してください。

## 8.2 UI状態の同一性

eguiの永続IDまたは入力状態がタブの表示位置へ不適切に追従しないようにしてください。

並べ替え前後で、タブのホバー、ドラッグ、クリック、閉じる操作が別の文書へ誤適用されないことを確認してください。

# 9．左右分割ビュー

## 9.1 基本仕様

初期実装では、同一ウィンドウ内を最大2ペインへ左右分割できるようにしてください。

概念上の表示は次のとおりです。

```text
┌─────────────────────────────────────────┐
│ メニュー・共通操作領域                  │
├───────────────────┬─────────────────────┤
│ 左側のタブ／表示  │ 右側のタブ／表示    │
│                   │                     │
│       PDF         │        PDF          │
│                   │                     │
└───────────────────┴─────────────────────┘
```

タブバー、ツールバー、サイドバーをどの階層へ配置するかは、既存UIと操作の明確さを調査して決めてください。

ただし、各タブがどのペインへ所属し、どの文書がフォーカス中か判別できるようにしてください。

## 9.2 分割作成

単一ペインの状態で、タブをPDF表示領域へドラッグした場合、左右分割のドロップ候補を表示してください。

少なくとも次を区別できるようにしてください。

* 左側へ分割する。
* 右側へ分割する。
* 分割せず、元の操作を取り消す。

必要であれば、対象ペインへ通常移動する中央領域を設けて構いません。

ドロップ候補の具体的な面積、色、透明度、アニメーションは決め打ちしません。次を満たす最小の表示を選んでください。

* 分割後の配置方向が事前に分かる。
* PDFの内容を完全に隠さない。
* 誤操作しやすい小さすぎる領域にしない。
* ドラッグしていない通常時には表示しない。
* 注釈編集UI、コンテキストメニュー、検索欄などの前面UIへ誤って表示しない。
* ウィンドウ外や別UI領域へのドロップで分割しない。

分割作成には、元のペインへ少なくとも一つのタブが残る必要があります。

一つしかタブがない状態で、移動によって片側が空になる分割を作成しないでください。

## 9.3 分割後の選択

分割作成後は、次を満たしてください。

* ドラッグしたタブを新しいペインで表示する。
* 元のペインには適切なタブが残る。
* 新しく作成したペインをフォーカスするかどうかを、一貫した規則で決める。
* ページ位置、ズーム、検索、選択、編集履歴を維持する。
* タブ移動だけを理由に文書を再オープンしない。
* 両側の表示が独立してスクロール、ズーム、ページ移動できる。

## 9.4 分割比率

左右ペインの境界をドラッグして、幅を変更できるようにしてください。

次を満たしてください。

* 初期比率は実用的な値とする。
* 片側が操作不能な幅まで縮まらない。
* ウィンドウサイズ変更後も比率または幅を有効範囲へ収める。
* セパレーターの操作とPDFパン、テキスト選択、タブドラッグを混同しない。
* FitWidthとFitPageは各ペインの実際の表示領域に基づいて再計算する。
* 比率変更だけで不必要に文書状態を破棄しない。
* 旧サイズのタイルを安全に暫定利用できる場合は、既存方針を維持する。

具体的な最小幅、初期比率、セパレーター幅は、現行UIと最小ウィンドウサイズを確認して決めてください。

# 10．ペイン間のタブ移動

## 10.1 タブバーへの移動

分割後、タブを反対側ペインのタブバーへドラッグし、そのペインへ移動できるようにしてください。

次を満たしてください。

* 移動先の挿入位置を選べる。
* 移動先のタブ順へ正しく反映する。
* 移動元から同じタブを削除する。
* 文書を複製しない。
* 移動後も文書状態を維持する。
* 移動中の非同期応答を誤ったタブへ適用しない。
* 移動先の選択状態を一貫した規則で更新する。

## 10.2 表示領域への移動

既に2ペイン存在する場合、表示領域へのドロップで3番目のペインを作成しないでください。

必要に応じて、既存の反対側ペインへ移動する操作として扱ってください。

具体的なドロップ領域は、分割作成時のUIと矛盾しないように設計してください。

## 10.3 空ペインの縮約

タブ移動またはタブ終了によって片側ペインが空になった場合は、分割を解除して単一ペインへ戻してください。

次を満たしてください。

* 残ったペインのタブと選択状態を維持する。
* 分割解除で文書を再オープンしない。
* 残ったPDFのページ位置とズームを維持する。
* PDF操作中の無効なドラッグ状態を残さない。
* セパレーター状態を残さない。
* セッション保存時に空ペインを保存しない。

# 11．フォーカスと共通UI

## 11.1 フォーカス中ペイン

PDF領域、タブ、またはペイン固有UIを操作した場合、そのペインをフォーカス中として扱ってください。

フォーカス状態を色差だけへ依存させず、現在の選択タブまたは境界表示など、既存テーマと整合した方法で判別できるようにしてください。

過度に目立つ常時枠は必要ありません。

## 11.2 共通ツールバー

共通ツールバーを維持する場合、原則としてフォーカス中ペインの選択タブを操作対象にしてください。

対象には次を含みます。

* ページ番号。
* 前後ページ移動。
* ズーム。
* FitWidth。
* FitPage。
* 連続表示。
* 単一ページ表示。
* ハイライト作成。
* PDF内検索。
* 印刷。

フォーカスを切り替えた場合、表示内容と操作対象が同じ文書を指すようにしてください。

## 11.3 ショートカット

原則として、次の操作はフォーカス中ペインの選択タブを対象にしてください。

* `Ctrl+F`
* `Ctrl+S`
* `Ctrl+P`
* `Ctrl+Z`
* `Ctrl+C`
* `PageUp`
* `PageDown`
* ズーム操作
* 表示モード切替

テキスト入力欄または注釈コメント欄にフォーカスがある場合は、既存どおり文字入力と編集操作を優先してください。

`Ctrl+Tab`および将来追加される前タブ操作は、フォーカス中ペイン内のタブを対象とするか、別の規則を採用するかを調査して決めてください。

採用した規則を作業報告へ記載してください。

## 11.4 サイドバー

アウトライン、サムネイル、ハイライト一覧は、原則としてフォーカス中ペインの選択タブを表示対象にしてください。

サイドバー項目を操作した結果が、反対側ペインの文書へ適用されないことを確認してください。

# 12．注釈編集と一時UI

タブの並べ替えまたはペイン間移動によって、注釈編集状態を黙って破棄しないでください。

次を確認してください。

* 編集対象を文書またはタブへ対応付ける現在の方法。
* 未保存の注釈編集がある状態でのタブ移動。
* 注釈更新処理中のタブ移動。
* 編集対象タブを別ペインへ移動した場合の表示位置。
* 編集対象とフォーカス中ペインが異なる場合の扱い。
* タブ終了、全タブ終了、ウィンドウ終了との競合。

具体的には、既存の注釈編集制約を維持し、次のいずれかを一貫して採用してください。

* 編集状態を対象タブとともに移動させる。
* 未確定編集がある間は、該当する移動操作を明示的に拒否する。
* 対象タブへフォーカスを戻し、ユーザーへ確定または破棄を求める。

ユーザーの編集内容を通知なしに破棄しないでください。

# 13．非同期処理

タブの表示順または所属ペインが変化しても、非同期結果を正しい文書へ適用してください。

少なくとも次を確認してください。

* 文書オープン完了。
* 文書変更通知。
* タイル描画完了。
* テキスト選択完了。
* テキストスナップショット。
* 注釈ページ取得。
* ハイライト索引。
* 検索結果。
* サムネイル。
* 保存完了。
* 印刷完了。
* Undo完了。
* ワーカー切断。

次を防いでください。

* 並べ替え前のインデックスへ応答を適用する。
* 反対側ペインの同じ位置にある別タブへ応答を適用する。
* 閉じたタブの応答で別タブを更新する。
* 非表示タブの結果を、表示中タブの結果として描画する。
* 古いrevisionまたはgenerationの結果を受理する。

既存の文書ID、revision、generation、要求キーを再利用できる場合は、それを優先してください。

# 14．描画とキャッシュ

## 14.1 両ペインの描画

左右両方の表示タブについて、可視領域に必要なタイルを要求してください。

フォーカスされていない側も、画面へ表示されている限り描画対象です。

現在の「アクティブタブだけ結果を受理する」判定がある場合は、分割後の表示条件へ適合するか確認してください。

## 14.2 キャッシュ予算

既存のGPU LRUおよびサムネイル予算を尊重してください。

分割しただけで、各ペインへ同じ固定予算を無条件に複製し、アプリ全体の上限を倍増させないでください。

共有するか分配するかは、現行実装と性能を確認して決めてください。

採用した方針を作業報告へ記載してください。

## 14.3 描画優先度

両ペインの可視タイルが、非表示タブの先読みやサムネイル処理によって長時間阻害されないようにしてください。

フォーカス中ペインだけを常に優先して反対側が白紙になる状態は避けてください。

必要な場合は、両ペインの可視要求を最優先とし、その後に先読みを行ってください。

## 14.4 Fit計算

FitWidthおよびFitPageは、各ペインの実際のPDF表示領域を使用してください。

次を確認してください。

* 左右のペイン幅が異なる場合。
* セパレーター移動中。
* サイドバー開閉。
* ウィンドウサイズ変更。
* ツールバーまたはタブバー高さ。
* 単一ページ表示。
* 連続表示。
* 横長PDF。
* 高DPI。

一方のペインの寸法を、もう一方のFit計算へ使用しないでください。

# 15．メモリ休止

画面へ表示されている左右両方のタブを、非アクティブ文書として休止しないでください。

フォーカス中ではないが表示中のタブを、休止候補から除外してください。

次も維持してください。

* dirtyな文書を休止しない。
* 保存中または印刷中の文書を休止しない。
* 未確定の注釈編集を持つ文書を休止しない。
* 最も長く使用されていない非表示文書を優先する既存方針。
* 休止文書を再選択した場合の再開。
* 外部変更確認。

タブ移動だけで不要な休止または再開を発生させないでください。

# 16．セッション保存と復元

分割ビューの状態を、既存のセッション復元方針へ統合してください。

少なくとも次を保存・復元してください。

* タブの表示順。
* タブの所属ペイン。
* 各ペインの選択タブ。
* フォーカス中ペイン。
* 単一ペインまたは左右分割の状態。
* 分割比率。
* 各文書のページ位置、ズーム、表示モード。
* 既存のサイドバー状態。
* 既存の最近使った注釈色。

旧セッション形式は、単一ペインとして読み込めるようにしてください。

既存ユーザーのセッションファイルを、説明なく読めなくしないでください。

新しい形式では、次を検証してください。

* 空ペインを含まない。
* 同じタブが複数ペインへ重複所属しない。
* 存在しないタブを選択しない。
* フォーカス対象が存在する。
* 分割比率が有限かつ有効範囲内である。
* タブが0件の場合の状態が有効である。
* 一部のPDFが存在しない場合も、残りのタブを可能な範囲で復元する。
* 復元途中の非同期完了順によって、別ペインへ誤配置しない。

将来上下分割を追加しやすい永続化形式を検討してください。

ただし、今回使用しない任意個ペインの複雑な形式を先回りして実装する必要はありません。

* 破棄。

* 保存中または印刷中の終了待機。
* セッション保存失敗。
* 復元途中のウィンドウ終了。

未保存確認の対象を、表示位置インデックスだけで識別しないでください。

タブの移動後も、保存完了時に正しいタブを閉じてください。

片側最後のタブを閉じた場合は、分割を解除して残ったペインを維持してください。

最後のタブを閉じた場合は、従来の空状態へ戻してください。

既存方針で`--all-features`や`-D warnings`を使用している場合は、その方針に従ってください。

Dev Containerでは、`AGENTS.md`の現行コマンドを使用してください。

Windows GNU向けのdebugおよびreleaseビルドも、既存手順に従って確認してください。

GUI受入確認前に、`.codex/validation-lessons.md`を読んでください。

失敗した場合は、次を区別してください。

* 今回の変更による失敗。

* 環境不足。
* 製品コードへ到達する前の失敗。
* Windows固有の失敗。
* Linux固有の失敗。
* GUI自動操作環境の制約。
* 実機未確認。
* 特定DPI未確認。
* 特定入力機器未確認。

実行していない検証を成功として報告しないでください。

# 26．完了条件

次をすべて満たした時点で完了です。

1. 同一ペイン内でタブをドラッグして並べ替えられる。
2. 並べ替え後も文書状態が別タブへ混ざらない。
3. タブを表示領域へドラッグして左右分割できる。
4. 左右両方のPDFを同時に表示できる。
5. 各ペインを独立してスクロール、ズーム、ページ移動できる。
6. 左右ペイン間でタブを移動できる。
7. 片側が空になった場合に単一ペインへ戻る。
8. 最大2ペインを超えない。
9. フォーカス中ペインと表示中タブを区別できる。
10. ツールバー、サイドバー、ショートカットが正しい文書を操作する。
11. 両ペインの可視タイルが描画される。
12. 表示中のタブがメモリ休止されない。
13. 非同期結果が並べ替えまたは移動後も正しい文書へ適用される。
14. dirty、Undo、保存、印刷、注釈編集を壊さない。
15. タブ順、所属ペイン、分割比率をセッション復元できる。
16. 旧セッションを読み込める。
17. 既存の単一ペイン操作を回帰させない。
18. 将来の上下分割で、タブと文書の所有構造を全面変更する必要がない。
19. 不要な任意個ペイン基盤または神型を追加していない。
20. 実行した検証と未確認事項を正確に報告している。
