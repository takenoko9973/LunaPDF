# LunaPDF マウスホイールスクロール量・速度設定 改善指示書

## 1. 目的

LunaPDFのマウスホイールによるスクロール量をSumatraPDFに近づける。

あわせて、ユーザーがLunaPDF側からマウスホイールのスクロール速度を変更できる設定を追加し、設定内容を永続化する。

今回の中心は以下の2点である。

1. Windows上の既定スクロール量をSumatraPDF相当にする。
2. その基準値に対するスクロール速度をユーザー設定可能にする。

スクロールのアニメーション、トラックパッド挙動、入力システム全体の再設計は今回の対象外とする。

# 3. 確認済みの原因

現時点のLunaPDFは、

* `eframe 0.35.0`
* `egui 0.35.0`
* `winit 0.30.13`

系を使用している。

Windows上の`winit 0.30.13`では、通常の`WM_MOUSEWHEEL`について、

```text
WHEEL_DELTA = 120
    ↓
LineDelta(..., 1.0)
```

のように、1ノッチを基本的に`1.0 line`として上位へ渡す。

この処理ではWindowsの

```text
SPI_GETWHEELSCROLLLINES
```

による「1ノッチで何行スクロールするか」というシステム設定は反映されていない。

その後egui 0.35では、`MouseWheelUnit::Line`について概ね、

```text
delta × InputOptions::line_scroll_speed
```

として扱い、native環境での既定`line_scroll_speed`は`40.0`である。

したがって現在のLunaPDFでは、一般的なマウスホイール1ノッチあたり概ね、

```text
40 logical points
```

のスクロール量になる。

一方、現在のSumatraPDFではWindowsの`SPI_GETWHEELSCROLLLINES`を参照し、通常スクロールの1行あたりの基準量として16を使用している。

Windowsの一般的な設定、

```text
1ノッチ = 3行
```

であれば、

```text
16 × 3 = 48
```

となる。

そのため、一般的な環境では現在のLunaPDFの約40に対し、SumatraPDFは約48となり、LunaPDFの方がスクロール量が小さい。

この差を今回修正する。

# 4. 決定済みの基本方針

## 4.1 WindowsではSumatraPDF相当を100%とする

Windowsでは、

```text
Sumatra互換基準スクロール量
= 16 × Windowsのホイールスクロール行数
```

を基本とする。

例：

| Windows設定 | LunaPDF 100%時 |
| --------: | ------------: |
|        1行 |            16 |
|        2行 |            32 |
|        3行 |            48 |
|        5行 |            80 |

通常のWindows既定値が3行なら、

```text
48 logical points / notch
```

程度になることを期待する。

「48」という固定値だけをハードコードするのではなく、可能な限りWindowsの現在のホイール設定を尊重すること。

Windowsの設定取得には既存依存またはWindows APIを使用し、新規の重量級依存を追加しないこと。

---

## 4.2 LunaPDF独自の速度設定

Sumatra互換基準値に対して、LunaPDF側のユーザー設定倍率を掛ける。

概念上は、

```text
effective_scroll_amount
    = system_compatible_base
    × user_scroll_speed
```

とする。

ユーザーUIでは内部のポイント値を直接設定させず、百分率で表示する。

例：

```text
マウスホイールのスクロール速度
100%
```

100%を既定値とする。

Windowsでは、

```text
100% = SumatraPDF相当
```

とする。

Windowsのホイール設定が3行なら、例えば以下となる。

| LunaPDF設定 | 1ノッチあたりの目安 |
| --------: | ---------: |
|       50% |         24 |
|       75% |         36 |
|      100% |         48 |
|      125% |         60 |
|      150% |         72 |
|      200% |         96 |

設定範囲は過度に広げる必要はない。

目安として、

```text
25% ～ 300%
```

程度を想定するが、既存UIとの整合性を確認した上で最終的な刻み幅やコントロールはCodexが決定してよい。

「既定値に戻す」操作を自然に提供できる既存UIがある場合は追加する。

# 5. Windows側の補正

## 5.1 `SPI_GETWHEELSCROLLLINES`

Windowsでは`SPI_GETWHEELSCROLLLINES`から現在の行数を取得する。

取得できた正の行数について、

```text
16 × lines
```

をSumatra互換基準値として使用する。

例：

```text
SPI_GETWHEELSCROLLLINES = 3
→ 16 × 3
→ 48
```

実装方法は現在のWindowsプラットフォーム層を確認してCodexが決定すること。

Windows API呼び出しを`app.rs`へ無秩序に直接追加せず、既存の`src/platform/windows/`の責務分離に合うならそこへ配置する。

ただし、このためだけに過剰な抽象化層や汎用入力フレームワークを新設しないこと。

---

## 5.2 Windows設定取得失敗時

API呼び出しが失敗した場合にもスクロール不能にしてはならない。

合理的なフォールバックを用意すること。

フォールバック値は、一般的なWindows環境でSumatraPDF相当に近くなる、

```text
3行
```

またはそれと等価な基準値を第一候補とする。

詳細は既存エラー処理方針と合わせて決定する。

この程度のOS設定取得失敗を毎回ユーザー向けエラーとして表示する必要はない。

---

## 5.3 「1画面ずつスクロール」設定

`SPI_GETWHEELSCROLLLINES`には通常の正の行数以外に、Windows側の「1画面ずつスクロールする」設定を表す特殊値が存在する。

今回、この特殊ケースを正確にSumatraPDF同等へ再実装するためだけに、

* `WM_MOUSEWHEEL`の独自フック
* egui/winit入力経路の置換
* ScrollArea全体の再実装

などへ範囲を広げてはならない。

現在のegui/winit構成で簡潔かつ安全に扱えるなら対応してよいが、そうでなければ通常の行スクロールへ安全にフォールバックし、その制約をコメントまたはテストで明示する。

通常利用である正の行数設定を優先する。

# 6. eguiへの反映方法

現在のPDF表示は`egui::ScrollArea`を使用している。

まず、

```text
egui::InputOptions::line_scroll_speed
```

を適切に設定する方法で今回の要件を満たせるか確認すること。

満たせる場合は、既存のScrollAreaへ個別にホイール処理を追加するより、eguiの既存入力機構を利用することを優先する。

以下のような実装は、必要性が確認できない限り行わない。

* PDF表示領域ごとの独自MouseWheelイベント消費
* `WM_MOUSEWHEEL`の直接横取り
* ScrollArea内部状態の模倣
* 独自スムーズスクロールエンジン
* egui自体のfork
* winit自体のfork

今回必要なのは、通常のホイールスクロール量の補正である。

## 7. 必須コードコメント

Windows用のSumatra互換補正を実装する箇所には、**なぜこの補正が存在するのか分かる日本語コメントを必ず追加すること。**

コードコメントは英語ではなく、日本語で記述すること。

コメントには少なくとも以下の趣旨を含める。

1. 現在LunaPDFが使用する`winit 0.30.x`では、Windowsの`WM_MOUSEWHEEL`を`LineDelta(1.0)`相当として扱い、`SPI_GETWHEELSCROLLLINES`を反映しない。
2. そのためLunaPDF側でWindowsのホイール行数を取得して補正している。
3. この補正は、Windowsのユーザー設定を尊重しつつ、SumatraPDFに近いスクロール量にすることを目的としている。
4. 将来、LunaPDFが使用するwinit/eframeがWindowsのシステムホイール速度を上位へ反映する実装へ更新された場合、この補正をそのまま残すと倍率が二重適用される可能性がある。
5. winit/eframe更新時には、この補正がまだ必要か必ず再確認すること。

コメント例の趣旨は以下とする。

```rust

// 1ノッチが LineDelta(1.0) 相当として渡され、SPI_GETWHEELSCROLLLINES による
// Windows の「1ノッチで何行スクロールするか」という設定は反映されない。
//
// そのため LunaPDF 側で Windows のホイール行数を取得し、1行あたり16を基準として
// 補正する。これは Windows のユーザー設定を尊重しつつ、SumatraPDF に近い
// スクロール量を得るための暫定的な補正である。
//
// 将来 winit / eframe を更新し、winit 側で Windows のシステムホイール速度が
// すでに反映されるようになった場合、この補正を残すと倍率が二重適用される。
// 依存ライブラリ更新時には、この補正がまだ必要か必ず再確認すること。
```

実際の変数名や配置に合わせて文章は調整してよい。

ただし、単に、


のような理由だけを書かないこと。

**現在のwinit 0.30.xの挙動、LunaPDF側で補正する理由、将来撤去・再確認が必要になる条件まで、日本語コメントとして残すこと。**

また、今回新たに追加する設定保存、Windows API取得、フォールバック処理などについても、説明が必要な箇所のコメントは既存プロジェクト方針に合わせて日本語で記述すること。

# 9. スクロール速度設定の永続化

スクロール速度は、

* 現在開いているPDF
* ページ位置
* タブ配置
* 分割表示

などのセッション情報ではなく、アプリケーション全体のユーザー設定である。

したがって、原則として文書セッション状態へ混在させない。

現在LunaPDFには主として`session.json`による永続化が存在するため、最新構成を確認した上で、アプリ設定用の保存先を追加する。

Windowsでは概念的に、

```text
%APPDATA%\LunaPDF\
├─ session.json
└─ settings.json
```

のような分離を想定する。

ただし、現在すでにアプリ設定用ストアが追加されている場合はそれを利用すること。

新規に作る場合も、このスクロール設定だけのために複雑な設定フレームワークを構築しない。

最低限、

```text
wheel_scroll_speed
```

相当の値を保存・復元できればよい。

将来的に他の設定を追加できる程度の素直な構造にしつつ、YAGNIを守ること。

# 10. 設定UI

既存のメニュー構成を確認し、自然な場所にスクロール速度設定を追加する。

表示名称は原則として、

```text
マウスホイールのスクロール速度
```

とする。

内部値ではなく、

```text
100%
```

のようにユーザーへ表示する。

100%が既定値であることが分かるようにする。

設定変更は可能なら即時反映し、アプリ再起動を要求しない。

設定変更後に新しく開いたPDFだけでなく、現在表示中のPDFにも反映されること。

UI実装のためだけに大規模な設定ダイアログを新設する必要はない。

ただし、現在すでに設定画面または設定メニューの設計が存在するなら、それに統合する。

---

# 11. トラックパッド

今回の設定対象は原則として、

```text
MouseWheelUnit::Line
```

に相当する通常のマウスホイール入力とする。

高精度トラックパッドなどから来る、

```text
MouseWheelUnit::Point
```

の入力まで同じ倍率で変更しないこと。

eguiではLine入力とPoint入力が区別されているため、その区別を維持する。

今回の修正によって、

* Precision Touchpad
* タッチパッド慣性スクロール
* Point単位の高精度入力

の感触を不必要に変更しないこと。

トラックパッド速度設定は今回追加しない。

---

# 12. 単一ページモード

LunaPDFには、単一ページ表示時に端へ到達したホイール操作を隣接ページ遷移へ変換する独自処理がある。

今回のスクロール量変更によって、

* ページ末端へ到達しただけで意図せず次ページへ飛ぶ
* 1ノッチで複数ページ進む
* Fit Page時のページ送りが壊れる
* トラックパッドのページ遷移閾値まで変化する

といった回帰を起こさないこと。

特に既存の、

```text
single_page_wheel_steps
SinglePageWheelState
TRACKPAD_PAGE_THRESHOLD_POINTS
```

周辺について、通常ホイール速度変更との責務が混ざらないか確認する。

必要がなければ既存のページ遷移ロジック自体は変更しない。

---

# 13. スムーズスクロール

egui 0.35は離散的なホイール入力を内部で数フレームに分けて平滑化する。

そのため、SumatraPDFとスクロール総量を一致させても、時間方向の動き方が完全には一致しない可能性がある。

今回はまず、

```text
1ノッチあたりの最終移動量
```

を合わせる。

以下は今回変更しない。

* eguiの平滑化係数
* 慣性
* 補間方式
* スクロールアニメーション時間
* SumatraPDFのスムーズスクロールアルゴリズムの模倣

実機確認後に「総移動量は合っているが動きだけ違う」という問題が残った場合、別タスクとして扱う。

スクロール量調整とアニメーション調整を同時に行わないこと。

# 17. 実装上の原則

* KISSを優先する。
* YAGNIを守る。
* 現行構成を尊重する。
* 無関係なリファクタリングを行わない。
* 新規依存は極力追加しない。
* Windows固有コードは可能な限りWindowsプラットフォーム層へ閉じ込める。
* OS固有値とユーザー設定倍率を混同しない。
* セッション状態とアプリ設定を混同しない。
* 通常マウスとPoint単位トラックパッド入力を混同しない。
* Sumatra互換の「距離」とスクロールアニメーションの「時間特性」を混同しない。
* 既存テストを削除・弱体化して通さない。
