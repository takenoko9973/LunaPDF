### 実画面の再現と履歴境界

WSLg/X11上のLunaPDF対象ウィンドウだけを読み取り、1200 × 900 physical pixels、連続表示、FitPage、サイドバー閉の条件で確認した。

- コミット`240274b`のreleaseビルド：ページ右半分がページ背景色`(245, 245, 245)`のまま残った。
- 次のコミット`6945d34`のreleaseビルド：右端まで描画された。
- 作業開始時点の最新`main`のreleaseビルド：右端まで描画された。

旧ビルドと`240274b`の欠落は描画待ちではなく、複数回の対象ウィンドウ検査後も残る恒久的な欠落だった。

### 最初の不整合

再現コミットへ一時ログを追加し、同一generationのタイル要求とMuPDF返却を照合した。

- UI側の`TileGrid`が要求したページ画素幅：749px
- MuPDFが変換後のページ境界から得た画素幅：748px
- UI側の最右列`TileSpec`：`pixel_x=512, pixel_width=237`
- MuPDF返却の最右列`TileSpec`：`pixel_x=512, pixel_width=236`
- 結果：`TileCacheKey`が一致せず、`tile_result_is_current()`が最右列を破棄した。
- 左列は`pixel_x=0, pixel_width=512`で一致するため表示され、右列だけが欠落した。

したがって、期待値から最初に外れる地点は、FitPage配置や可視範囲ではなく、フロントエンドの`TileGrid`とMuPDFの変換済みページ画素境界の丸め規則である。

### 修正前に失敗する回帰テスト

報告PDFと同じページ寸法と実測スケール`0.94242066`を使うテスト条件を追加した。次のコマンドで1件実行し、修正前の失敗を確認した。

```text
docker compose -f .devcontainer/compose.base.yml exec workspace cargo test landscape_fractional_dpi_keeps_request_and_rendered_tile_edges_identical -- --nocapture
```

実結果：失敗。

```text
assertion `left == right` failed
left: 748
right: 749
```

### 修正と再検証

MuPDFの`fz_round_rect`は、浮動小数点誤差で整数境界を1pxまたぐことを避けるため、左上を`floor(value + 0.001)`、右下を`ceil(value - 0.001)`で丸める。`src/render/tiles.rs`の`scaled_extent()`をこの規則へ統一した。

- 0.001はMuPDF 0.8.0同梱ソースの`fz_round_rect`に由来する。
- 既存のi32表現範囲と巨大ページの可視範囲限定方法は変更せず、1px差の原因だった±0.001の誤差吸収だけを合わせた。
- 固定の描画位置補正、許容範囲を広げるタイルキー照合、無条件の全ページ描画は追加していない。

修正直後の対象テスト結果：成功。

```text
test render::tiles::tests::near_integer_edge_uses_mupdf_rectangle_rounding ... ok
test pdf::mupdf_backend::tests::landscape_fractional_dpi_keeps_request_and_rendered_tile_edges_identical ... ok
```

最初の実装ではMuPDFの安全整数範囲までUI側の受理条件を変えたため、全テストで巨大ページの可視範囲限定テスト2件が失敗した。MuPDFと同じクランプへ変える案も要求数を3150件から378件へ変えたため採用しなかった。最終的に既存の巨大ページ契約は維持し、今回の原因である±0.001の丸めだけを変更した。修正後の再検証結果は最終検証節へ記載する。

修正後の最新releaseをWSLg/X11で再ビルドし、`260304_GaN.pdf`、連続表示、FitPage、1200 × 900 physical pixels、サイドバー閉で再確認した。対象ウィンドウのページ右端までPDF画素が描画され、再現時に連続していたページ背景色だけの右半分はなかった。

## 2. 一体型タブと動的タブ幅

### 確認済みの変更

- タイトル、dirtyマーカー、閉じる領域を一つのタブ矩形内へ統合した。
- 全タブを同じ幅で、最大240ptから最小96ptまで縮小する。
- eguiのタブ間隔を総幅へ含め、最小幅へ達した後だけ横スクロールする。
- 選択時だけ、選択タブを一度表示範囲へ移動する。
- 閉じる領域とタイトル領域を分離し、完全なパスをツールチップ表示する。

### テスト

- 0、1、複数タブの幅計算
- タブ数増加時の単調縮小
- 間隔を含む総幅
- 最小幅到達後の横スクロール
- タイトル領域と閉じる領域の非重複
- 選択タブの一度だけの表示移動
- 非選択タブを閉じた際に、選択タブの表示位置へ戻さないこと

最終の実画面確認と全体テスト結果は、検証完了後に追記する。

### 実画面確認

同じPDFの一時コピーを異なる日本語名・英数字名で開き、WSLg/X11の1200 × 900対象ウィンドウ上端を検査した。

- 1タブ、2タブ：各240pxの最大幅で固定され、残りの幅へ引き伸ばされなかった。
- 5タブ：各約236pxへ均等縮小し、タブバー幅へ収まった。
- 10タブ：各約118pxへ均等縮小し、横スクロールは発生しなかった。
- 20タブ：各96pxの最小幅で固定され、横スクロールへ移行した。
- 起動時に最後の20番目を選択したケースで、選択タブのタイトルから閉じる領域までが右端へ自動表示された。
- 長い日本語名、長い英数字名、短い日本語名で24pxの閉じる領域が維持された。
- 5タブ中の1番目を選択した状態で非選択の2番目の閉じる領域をクリックすると、2番目だけが閉じ、1番目の選択状態は維持された。閉じる操作による選択の誤発火はなかった。

dirty・印刷中状態の実画面確認は未実施。

### 独立レビュー後の修正

最終レビューで、選択タブより左の非選択タブを閉じると、選択文書は同じままでもindexの減少を選択変更と判定し、選択タブへ横スクロールする問題が見つかった。close後の表示移動を、閉じたタブが選択中だった場合だけに限定した。非選択タブのcloseでindexだけが変わる回帰テストを追加し、対象テストとLinux全テストで成功を確認した。

修正後の独立再レビューでは、この指摘の解消と、新たな受け入れ停止事項がないことを確認した。

## 3. テキスト選択範囲の不一致

### 再現

MuPDFで生成した`ABCDE`の1行PDFを用い、先頭文字中央から末尾文字中央まで選択した。

- ドラッグ中のglyph範囲：`ABCDE`
- 修正前のMuPDF point selectionによる確定範囲：`BCD`
- 欠落：開始文字`A`と終了文字`E`

### 原因と変更

プレビューは両端を含むglyph index範囲を使用していたが、確定処理だけが開始点・終了点をMuPDFのpoint selectionへ再入力し、異なる境界規則へ変換していた。

選択の正を共通の両端包含glyph範囲へ統一し、次の4用途が同じ文字列とQuadを使うよう変更した。

1. ドラッグ中プレビュー
2. 確定後表示
3. コピー文字列
4. Highlight注釈

1文字、両端、逆方向、文字外終了、複数行、非水平Quadのテストを追加した。最終の全体テスト結果は検証完了後に追記する。
