# LunaPDF：Codex指示体系・Skill・ドキュメントの全体最適化 実装指示書

作成日：2026-10-21  
対象：`takenoko9973/LunaPDF`（主対象）、`takenoko9973/my-codex-toolkit`（共通設定の影響調査と限定的改善）  
参照時点：LunaPDF `main` = `815521406`、my-codex-toolkit `main` = `a87328670`（着手時に再確認すること）

## 0. 結論と最優先要件

**目的は、Codexの判断品質・検証能力・開発環境の安全性を落とさず、常時注入される指示、条件付きで読む資料、専門Skill、ビルド・テストの役割を整理すること。** 文書を短くすることやSkillを増やすこと自体を成果にしない。ソースの実際の仕様と、過去の指示・測定・計画を混同しない。

**確定した基本方針：LunaPDF専用の新規Skillは、今回の標準作業では作成しない（追加数0を初期案とする）。** 一般的な検証判断は`AGENTS.md`と既存検証マトリクス、再現可能な環境操作は安定した運用手順、過去の検証失敗は履歴文書で扱う。下記「Skill採用ゲート」を満たす具体的な反復ワークフローが確認されたときだけ、用途を限定した**リポジトリ内**Skillの導入を提案する。共通Skill配布先へのLunaPDF専用Skill追加は行わない。

この指示書による許可は、各リポジトリの現在の変更状況と既存のCodex権限契約を超えない。root/writer/レビュー/コミット所有権については有効な共通ルールを守る。タスクは受入可能な単位に分けるが、agent枠を埋めるために分割しない。

### 絶対に変更しないもの

- LunaPDFのPDF閲覧・保存・検索・印刷等の製品の振る舞い、公開API、永続化形式、既存の有効なテストの期待値。文書修正を理由に製品仕様を変更しない。
- DockerfileのRustツールチェーン／ベースイメージのバージョンを固定する施策。ソースのWindowsファイルシステムからWSL側への移転。
- 既存のDockerイメージ、コンテナ、Volume、Cargo/sccacheキャッシュの無断削除・prune・`down -v`。既存作業ディレクトリやGit履歴の破壊的変更。
- 既存の歴史的な設計書・実装指示書・計測記録の内容を、現在の仕様に見せるために書き換える行為。大量の移動・改名・削除。
- GUI実機操作／Computer Use／スクリーンショット／OCRの自律的な追加実行。現在の「ユーザーの明示指示時のみ」の制限を維持する。
- `my-codex-toolkit/config.toml`のmodel、reasoning effort、plugin有効化、並列上限、記憶等を、実証や個別要件なしに変更すること。インストーラーを実行して利用者の`%USERPROFILE%\.codex`を自動更新すること。

## 1. 調査で確認済みの現状とリスク

1. LunaPDFのルート`AGENTS.md`は、コミット・文書配置・Dev Container・GUI制限・検証・バージョンを記載する。一方、共通`my-codex-toolkit/AGENTS.sync.md`にもコミット、検証、文脈節約、agentの役割・コミットがある。**同一事項でも、共通設定を入れていない他の利用者に必要なLunaPDF固有の基本契約は短く残す。** 機械的な重複削除をしない。
2. LunaPDFの`AGENTS.md`にある`docker compose -f .devcontainer/compose.base.yml exec ...`やWindows GNUの長い固定コマンドは、タスクごとのCompose project/workspaceを識別せず、誤ったcheckoutを検証する危険がある。現在の実測報告では、既存workspaceを識別して`-p`を使用する運用、並列時だけ`cache-parallel.compose.yml`を適用する運用が示されている。
3. `docs/tasks/development-environment/verification-matrix.md`はすでに存在する。`docs/tasks/development-environment/261021_lunapdf_test_cache_optimization_report.md`は実測記録であると同時に日常の運用手順を含む。日付付き報告を将来の唯一の運用契約として参照し続けると陳腐化しやすい。
4. `.codex/validation-lessons.md`は過去の実GUI受入検証の問題を詳細に残しており、冒頭の現行方針は`AGENTS.md`・検証マトリクスと重なる。本文の歴史的事例は保護し、現在の適用条件だけ明瞭にする。
5. `.codex/rules/docker.rules`は`prefix_rule(pattern=["docker", "compose"], decision="allow")`という広い規則。実行権限への影響は使用中のCodexのルール仕様で検証すること。**破壊的なCompose操作まで無条件許可され得るなら優先的に是正**する。挙動未確認のまま危険を断定しない。
6. LunaPDF側には現時点で`.agents/skills/*/SKILL.md`が見当たらない。共通`my-codex-toolkit`には`agent-config-maintainer`を含むSkill群があり、Windows 10の画面取得Skillは明示的なGUI検証が許可されていない通常作業では起動すべきでない。GUI制限を避けるための新Skillを作らない。
7. `docs/tasks/`には歴史的な指示・報告が32ファイル、約646KBある。**存在自体が毎回のトークン費用を生むわけではない。** 長い歴史文書の常時・網羅読み込みと、歴史文書を現行仕様だと誤認することが問題である。
8. `docs/tasks/initial-design/pdf-viewer-plan-design.md`は初期設計であり、現行動作の唯一の正本ではない。`docs/platform-gui-validation.md`・`docs/performance-measurement.md`は特定時点の検証記録。現行仕様の正本が別途あるか、着手時に再検索する。ない場合は下記の限定的な現行仕様整備を行う。
9. `.vscode/tasks.json`には`cargo`へ`--release`のみを渡すタスクなど、古い可能性のある定義もある。**今回の本筋は指示・文書・Skillであり、周辺設定に不具合を疑っただけで無関係な修正を開始しない。** 再現した場合は独立した改善候補として扱う。
10. `my-codex-toolkit`は`AGENTS.sync.md`を利用者のグローバル`AGENTS.md`へ同期する。共有`agents/*.toml`も同期され、`config.toml`にはローカル情報を保持する処理がある。インストール先の編集ではなくソースを評価する。ただし**共通ソースへの変更は他プロジェクトへの影響を個別に検証**する。

着手時には、最新コミット、作業ツリーの既存差分、他者の実行中タスク、既存AGENTSの適用範囲を確認し、他者の変更を消さない。上記の現状から変化した項目は実測・読取りで更新する。必須でない全ソース・全履歴・全Skillの全文再読をしない。

## 2. 責務の確定：各種ファイルの単一の役割

| 配置 | 責務 | 常時/条件付き |
|---|---|---|
| `my-codex-toolkit/AGENTS.sync.md` | プロジェクト非依存の根本規則、agent所有権、検証・スコープ制御 | 全プロジェクト向け。内容変更には広い影響審査 |
| `LunaPDF/AGENTS.md` | LunaPDF固有の不変条件、安全境界、最小の参照先・分岐条件 | LunaPDF作業で常時。長いコマンドは置かない |
| `docs/tasks/development-environment/verification-matrix.md` | 変更種別→最小テスト→拡張条件→結果区分 | テスト選択が必要な場合に参照 |
| `docs/development-workflow.md`（新規候補） | 実際のCompose/project/workspace照合、キャッシュ、実行コマンド、復旧・ロールバック | Dev Containerやビルド環境を操作する場合に参照 |
| `docs/current-spec.md`（新規候補） | 現行実装で確認できたユーザー観測可能な仕様、条件、制約、未確認範囲 | 振る舞い・仕様に影響する場合に参照 |
| `.codex/validation-lessons.md` | 過去に無効だった受入手段、測定の限界と教訓 | 明示的なGUI/性能受入時のみ関連節を読む |
| `docs/tasks/README.md`と`docs/tasks/**/*` | 過去の作業指示・計画・報告の索引と履歴 | 明示指定または実装経緯の調査時のみ |
| `.agents/skills/*` | 条件付きで起動する、独立した複雑な反復ワークフロー | 採用ゲート通過時だけ存在させ、必要時のみ展開 |
| `my-codex-toolkit/skills/*` | 複数リポジトリで使う一般化された専門手順 | 名前・descriptionで限定選択 |

**優先する原則**：常時規則は短く、詳細は適用条件付きで参照する。ただし、参照先だけに安全上の必須ルールを閉じ込め、読む前の破壊的実行を許す設計は避ける。コード/テストを現行挙動の証拠とし、過去の計画や報告から未確認の仕様を創作しない。歴史文書は当時の証拠であり将来の命令ではない。

## 3. Task A：LunaPDFのAGENTSと検証・Docker運用の整理（優先・実装対象）

**目的**：通常タスクで無駄な読み込み・ビルド・GUI操作を増やさず、誤checkoutへの`exec`や危険な環境操作を防ぐ。既存の受入能力を維持する。

### 実装内容

1. `AGENTS.md`からWindows GNU debug/releaseを含む長いコマンドと、Compose projectを特定せず実行するコマンドを削減し、安定した運用文書への**条件付き参照**に置き換える。Windows GNUのビルド手段自体を消さず、運用文書には既存の正確な手順を残す。
2. `AGENTS.md`に、Dev Containerへ`exec`する前に**検証対象checkoutの実パスと、稼働containerがbindしているworkspaceのマウント元が一致することを確認する**規則を簡潔に置く。Compose project名・container名を推測しない。単なる文書調査タスクには確認を強制しない。
3. 逐次開発では既存workspaceとCargo incrementalを優先し、独立した別checkoutが実際にある並列検証では必要に応じてcache-parallel overlayを使う。SkillやAGENTSの指示だけでworktree/独立コンテナを作らない。現行のグローバルroot/writer運用と矛盾させない。
4. 新しい作業指示書を**作成するときだけ**`docs/tasks/README.md`による分類・索引・日付命名を適用する。既存文書への作業着手時に移動・改名しない。ユーザー提供の指示書に従う際も、不要な移動・索引更新を新たな前提にしない。
5. 「変更種別に応じた最小の自動テスト」「GUI実機操作は明示依頼時のみ」「実機未検証と実行合格は別」という必須原則は維持する。検証種別ごとの詳細表、ビルド構成、事故例を重複してAGENTSへ書かない。
6. コミット方針、`Cargo.toml`のversion一元管理、Windows側のソース配置、ユーザー文書・共有クリップボード・Docker資産保護など、別のグローバル設定を使わない利用者に必要なリポジトリ固有の要件は残す。グローバル側に類似記述があるという理由だけで削除しない。
7. `docs/development-workflow.md`の新設が既存報告への追記より保守的に優れることを確認した上で、日付に依存しない運用手順をそこへ移す。内容は既存の稼働project確認、`docker compose ... config/ps/exec/run`の正しい使い分け、checkoutマウント照合、共有イメージとregistry/target/sccacheの分界、並列overlay、Dockerfile変更後の明示build/再作成、削除禁止、調査用コマンド、必要時の切り戻しまで。存在しないコマンド/オプションを記載しない。報告書は当時の実測値として保持し、現行運用文書への短い案内を付けるにとどめる。
8. 検証マトリクスの役割を維持し、AGENTS・運用文書からの重複した詳細表は削る。`.codex/validation-lessons.md`冒頭を短い「現行方針はマトリクスを参照、以下は過去事例」に整理し、歴史本文は原則編集しない。
9. `.codex/rules/docker.rules`の実際の許可範囲を**ルール評価機能や仕様、非破壊の静的確認**で評価する。`docker compose down -v`等を実行してテストしない。広範囲allowが破壊的操作の確認省略につながることが確認できたら、互換な狭い許可へ変更するか危険な許可を解除する。ルールの仕様や許可動作が検証できなければ変更せず、未確認リスクと具体的な判断材料を報告する。`exec`経由の任意コマンドを安易に全面許可しない。

### 受入条件

- 古い固定ComposeコマンドをAGENTSから無くし、正しい対象checkout/projectへ到達する運用手順を一箇所から辿れる。
- 逐次、独立した並列、Dockerfile更新、存在しない既存containerの各ケースで選ぶ実行経路が矛盾しない。
- 通常のソース変更ではGUI操作・全テスト・不要buildを要求せず、明示的な実機検証の制限は維持する。
- マトリクス、運用手順、validation-lessonsの責務が分かれ、正しくリンクしている。
- Docker/ユーザー環境の既存資産を削除していない。実際のDocker buildは検証に不可欠な場合だけ行う。

## 4. Task B：現行仕様と歴史文書の導線（独立した文書Task）

**目的**：古い実装指示や初期設計から現行仕様を推測する無駄と誤りを減らす。数十件の歴史文書を都度読ませない。

1. `docs/`とルートを検索し、現行の製品仕様書が既にあるか確認する。既存の信頼できる現行正本があれば再利用し、同じ役割の文書を新設しない。
2. 現行正本がない場合、`docs/current-spec.md`を作成する。**実装済みで検証可能なユーザー観測可能な動作**を、PDFの読み込み・ページ移動・表示/スクロール・検索・タブ・選択/注釈・保存・設定/復元・印刷・OS依存の挙動など、確認できた範囲で整理する。既存の有効なテスト・実装と対応づける。網羅的な実装説明や単なるソースファイル一覧にはしない。
3. 初期設計での予定機能、旧版時点の検証成功、現在のコードからは断定できない挙動を、「現行実装済み」として書かない。判断不能なものは明確に未確認/要検証とし、現行契約が未確定の場合は推測で確定しない。今回の文書化だけを理由に機能追加やテストの期待値変更をしない。
4. `docs/tasks/README.md`に「ここは履歴索引であり、現在の規範は現行仕様・検証マトリクス・開発運用文書」という軽量な導線を置く。**従来の参照リンクを壊さず、既存の32ファイルの移動・改名・逐一書換えはしない**。過去の指示書に「実装済み」等の状態を一括付与しない。事実と不明を分ける。
5. 常時読むべきファイルを増やさない。目次と必要な章への参照は有効だが、`AGENTS.md`へ「作業前に全設計書/全報告書を読む」というルールを置かない。ルートREADMEの大規模新設など、目的外の人間向けドキュメント整備は行わない。

**受入条件**：現行仕様と初期計画の区別が明確。検索UI変更・PDF保存変更・文書だけの変更という代表例で、Codexが読むべき最小資料を説明でき、旧資料の誤引用や不要な全量読込を生まない。すべての相対リンクと記載したテスト/シンボルが実在する。

## 5. Task C：Skillの採否審査（初期結論は新設0）

### 適用基準

次の条件を**すべて**満たす場合にだけ、新規Skillを提案する。

1. 発動条件と**発動してはいけない例**を、タスク記述から明確に定義できる。
2. 繰り返し行う多段階・条件分岐・安全確認・ツール連携の手順が存在し、単なる短いルール/コマンド一覧ではない。
3. `AGENTS.md`、検証マトリクス、運用文書、既存の共通Skillだけでは再現性・誤操作防止が不十分である**具体的な根拠**がある。
4. Skillを導入した場合の重複と保守負担を上回る効果を説明できる。必要な場合だけ`SKILL.md`本体を読み、`references/`や`scripts/`はさらに必要時だけ使う。
5. LunaPDF固有なら`LunaPDF/.agents/skills/<skill-name>/SKILL.md`を用い、my-codex-toolkitのグローバル配布Skillへ混入しない。導入先が現行Codexで発見されることを確認する。

**今回の決定：上記の根拠が新たに得られない限り、Skillは作らない。** 将来候補を挙げることと、それを今すぐ実装することは別である。

### 候補と実際の動作（必要になった場合の仕様）

| 候補 | 発動条件（例） | 実行する処理 | 発動禁止例 |
|---|---|---|---|
| `lunapdf-gui-acceptance` | 「LunaPDFのWindows/WSLg実機UIを操作して受入検証して」とユーザーが**明示許可** | プラットフォーム・対象commit/実行ファイル・対象ウィンドウの特定→`.codex/validation-lessons.md`の該当教訓→安全なfixture・操作→実際の状態/保存PDFの検査→未検証範囲の記録 | 通常のRust修正、ヘッドレスUIテスト、単に「動作確認して」という曖昧な要求、スクリーンショット禁止中 |
| `lunapdf-workspace-verification` | 複数の独立checkoutとCompose projectがあり、既存runbookだけでは誤workspace操作が繰り返される | 実行対象checkout特定→Compose/マウント照合→既存container再利用判定→逐次/並列overlay選択→キャッシュ範囲の確認→非破壊で検証 | 読取り専用調査、単一既存containerの単純なテスト、worktreeを作ること自体 |
| `lunapdf-release-acceptance` | 明示的なWindows配布/release検査で、既存の`docs/windows-distribution.md`とpackaging手順だけでは反復時に具体的な手戻りがある | 対象versionと成果物の同一性確認→配布用build/署名等の既存要件→package検証→報告 | 通常のコミット、`cargo check`、未依頼のrelease作業 |
| `lunapdf-docs-sync` | 現行仕様とコードが頻繁に乖離する実例があり、複数の文書間同期を定期実施する | diffから挙動影響抽出→テスト/コード根拠確認→現行仕様の該当部分だけ修正→リンク検査→履歴の維持 | 無関係なコメント修正、古い計画書の全面書換え、一般文書の校正 |

`lunapdf-validation`（一般的なテスト選択）と`lunapdf-pdf-regression`（普通のCargoテスト実行）は**当面不採用**。既存マトリクスや実行可能なテストで十分なため、Skill化しても重複が増えるだけである。Windows 10画面取得の共通Skillも、LunaPDFの実GUI禁止を迂回する手段にしない。

新設を採用する場合は、`name`/`description`/適用例/非適用例/参照先/停止条件/必要な許可/テスト方法を記載し、既存の`agent-config-maintainer`と整合させる。冗長な履歴や一般原則を丸ごと転載しない。実装依存のないYAML frontmatter検査、少数の正負トリガー例、パス存在確認で受入を判断する。架空の利用量削減率を設定しない。

## 6. Task D：my-codex-toolkit共通設定の監査と限定的提案

**このTaskはLunaPDF固有の変更と分離する。** 共通設定に変更を加える必要性が実証されない場合、監査結果のみを返し、`my-codex-toolkit`の内容を変更しない。

1. `AGENTS.sync.md`、`skills/agent-config/agent-config-maintainer/SKILL.md`、`agents/*.toml`、`config.toml`、installerの`README.md`を対象に、**常時注入コスト、重複、役割の衝突、現行Codex仕様との適合、他のリポジトリへの波及**を評価する。ほかのSkill18件の全文精読・全面書換えを無条件に行わない。関連するものを選んで調べる。
2. 共通AGENTSと各agent TOMLの同じ趣旨の記述について、root/writer/reviewerの**別々のコンテキストに必要な意図的反復**と、単なる冗長な反復を識別する。文量を半分にする等の数値目標を先に置かない。Task境界、writer 1名制、rootのGit所有、reviewerの独立性、scope停止条件、実証ベースの検証方針を保持する。
3. `agent-config-maintainer`の「task-specific procedures into skills」があらゆる手順のSkill化を強制する解釈にならないよう、必要なら**複雑な反復ワークフローのみSkill、それ以外は参照文書/AGENTS**という判断条件を小さく明文化する。現状で誤動作の証拠がなければ変更しない。
4. `repo_explorer`が参照する`docs/agent-config/PROJECT_MAP.md`等は、「存在するとき・関連するとき」の補助候補であり、存在しない文書を毎回探させたり各リポジトリに新設させたりしない。実際のルーティング上の無駄が確認できた場合だけ調整案を出す。
5. 全体のモデル/effort、並列枠、メモリ、Computer Useプラグインの有効化は今回の文書整理の副次対象として**書き換えない**。これらが使用量の主因かどうかは、利用可能な実測記録があれば別表に整理する。Computer Useがenabledであることと、LunaPDFで常時起動されることを混同しない。
6. インストーラーを自動実行しない。共通ソースの変更提案を採用する場合は、他プロジェクトへの影響、既存smoke testの適用可能性、利用者環境への反映方法を明記して**別の受入単位**として扱う。インストール先`%USERPROFILE%\.codex`を直接編集しない。

**受入条件**：共通設定について「変更が必要な具体的箇所」と「現状維持が適切な箇所」を分け、各提案に根拠と波及範囲を付す。単なる文字数削減のために有効な責務境界を壊さない。

## 7. 検証・測定方法（実行していないものをPASSにしない）

### 安全な静的検証

- 各変更Taskの`git diff --check`、差分内容のscope確認、Markdownの相対リンク・セクションアンカーの解決、参照ファイルと参照されるテスト/型/コマンドの存在確認。文書Taskに意味のないRustテスト・Windows releaseビルド・GUI操作を行わない。
- Docker runbookのコマンドは**可能なら非破壊な**`docker compose config/ps`や`docker inspect`で、対象プロジェクト名とマウント元を確認する。起動済みcontainerがなくてもそのためだけに重い新規buildを行わない。
- `.codex/rules/docker.rules`の評価は仕様・rule match検査など非破壊な方法で行い、破壊的サブコマンドの実行による試験を禁止する。
- `my-codex-toolkit`のSkill/frontmatterを変更した場合に限り、その発見条件、意図する正負トリガー、適用先、必要なテストを確認する。installer scriptに変更を加えたときに限り既存smoke testを検討する。

### 行動シナリオの妥当性検査

結果を説明可能な正/負の代表例で確認する。

| シナリオ | 期待する選択 |
|---|---|
| 検索UIのRust修正 | 関連テスト＋必要時のヘッドレスUI。GUIを勝手に起動しない |
| README/作業指示の文言修正 | 差分・リンク確認。Cargoの全依存再ビルドなし |
| PDF保存ロジック修正 | 一時PDFの保存・再読込など意味的な自動検証。必要時だけ範囲拡大 |
| Windows印刷など実機依存変更 | 自動検証結果と実機未検証を分離。明示依頼なしにGUI実行しない |
| 既存の単一Dev Containerで逐次テスト | 同一checkoutの稼働containerへ`exec`、適合するtargetを再利用 |
| 別のcheckoutから`exec`しようとする | マウント元不一致を検出して停止・正しいプロジェクトへ切替 |
| 独立checkoutの並列ビルド | 各Compose project/targetを分離。要件を満たす場合のみsccache overlay |
| 明示的なGUI受入 | 対象と許可範囲を確認し、歴史的教訓を参照。必要な証拠のみ収集 |

### 計測と採否

- 変更前後の**常時注入ファイルの実バイト数・対応する文字/トークン推定**、条件付きで開く文書数、典型タスクに必要な読取範囲を区別する。履歴文書の総容量をそのままCodex使用量と説明しない。
- 可能なら実際のCodexログから、代表的な同等タスクでのtool call、読んだファイル、Computer Use回数、不要build/再検証回数、総使用量を比較する。利用できなければ未測定とし、削減量を推測で断定しない。
- 安全性・正確性・保守性の退行がないことを優先する。短くしても仕様判断を誤る、依存の必要な境界を見失う、検証がすり抜ける変更は棄却・修正する。

## 8. 実施順序・コミット・成果物

1. **監査**：現行コミット、差分、各文書の所有する情報、参照グラフ、実際のエージェント発動ルールを整理する。未知は未知として報告する。変更前の重複とリスクを具体的なパス・行・挙動で示す。
2. **Task A**：LunaPDF側の必須ルール、検証マトリクス、運用手順、validation-lessons、必要なら権限ルールを最小修正する。
3. **Task B**：現行仕様の正本がなければ、コード/既存テストの証拠に基づく正本を作成し、歴史資料との導線を整える。
4. **Task C**：Skillは原則追加しない。例外が必要と分かったときは、上記採用ゲートに基づき具体的な提案・正負トリガー・必要リソースを提示する。なしなら「追加不要」と明記して終了。
5. **Task D**：共通my-codex-toolkitの監査と影響評価。LunaPDFの修正と混ぜて共通設定を不用意に変更しない。真に必要な共通変更は別の受入単位に分離する。
6. **最終検証・報告**：リンクと文書構造、既存の安全境界、通常/並列/GUI受入のシナリオ、対象外事項の遵守を確認する。実測不能な使用量やGUI未検証を成功と書かない。タスクごとの実変更、差分理由、維持した契約、検査結果、残存リスクをコンパクトに報告する。

作業指示書を保存する場合の候補は`docs/tasks/development-environment/261021_lunapdf_codex_instructions_docs_skills_optimization.md`とし、既存の`docs/tasks/README.md`の索引を**新規文書の登録分のみ**更新する。既存指示書をこの場所へ移動・改名しない。内容を改めた各リポジトリで既存のGit運用・root/writerの所有権を守り、関連する受入が確認できた意味のある境界でコミットする。

### 最終報告に必ず含む事項

- 変更したファイルとその責務、対象リポジトリ/commit。変更不要と判定した主要ファイルと理由。
- `AGENTS.md`で残した常時指示と、条件付き資料へ移した情報の対応表。
- 現行仕様と歴史的資料の区分、発見不能な仕様や未確認事項。
- 新規Skillの**採用数（通常は0）と根拠**。採用時は名前、正負の発動条件、実行する手順、配置先、重複排除の根拠。
- Docker/Compose操作とGUI検証の安全条件が維持されたこと。実行した静的・意味的検査と、未実施の検査。
- 文脈消費・作業時間に関する実測値（得られた場合のみ）。実測できない場合は代替指標と限界。
- 共通my-codex-toolkitへ波及する変更・提案と、その適用範囲。他の利用者のCodex設定を無断更新していないこと。

**停止条件**：目的・スコープ・受入の根拠が揃ったところで終了する。根拠なく新しいSkill、テスト基盤、CI、スクリプト、互換層、抽象化、ドキュメント階層を増やさない。必要な追加改善は具体的な観測・根拠を添えて別件として提案する。
