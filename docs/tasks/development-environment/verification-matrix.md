# LunaPDF 検証マトリクス

変更の挙動・契約に関係する最小の自動検査から始め、受入条件や影響範囲に応じて広げる。変更がない領域の全テスト、全ターゲット、release・installer・クロスビルドを毎回実行しない。最終的に必要な受入範囲の検証は省略しない。

| 変更の種類 | まず行う検査 | 必要に応じて広げる範囲 |
| --- | --- | --- |
| Rustロジック・状態遷移 | 関連するユニットテスト。Rust変更では必要に応じて `cargo fmt --check` と `cargo check` | 共有経路・広い依存範囲へ影響する場合の関連テスト、Clippy、CI相当の検査 |
| 検索・UIの振る舞い | 関連ロジックテスト。widget入力や表示状態との接続を変えた場合はヘッドレスUIテスト | 変更したイベント経路・状態遷移の関連ケース |
| PDF保存・出力 | 一時PDFを使った保存後の再読込と意味的な構造・内容検査 | PDF機能の関連テストと、変更した保存経路 |
| Docker・Cargo・ビルド設定 | 既存Dev Container設定と実行中のComposeプロジェクト／workspaceを確認し、影響する設定・実行経路だけを検査 | 互換性や統合受入に必要な関連環境・ターゲット |
| Windows／OS統合 | 自動で確認できるロジック・設定・出力を検査 | 実機でしか確認できない範囲は理由・対象・代替不能な理由・方法を記録。ユーザーが明示的に依頼した場合だけ実施 |
| 文書・コメント・指示のみ | `git diff --check`、参照先・相対リンクの確認 | 振る舞いの検査ができない変更ではテストを追加しない |

Linux検証は既存のDev Container workspaceへの `exec` を優先する。[開発環境の運用手順](../../development-workflow.md)に沿ってCompose設定と実行中workspaceを照合し、名前やmount元を推測しない。`cargo check` は型・コンパイル検査であり、アプリの実行時動作を確認しない。既存のWindows／Linux検証経路とversion方針は維持する。

Docker/Cargoの実行コマンドと再利用・並列実行の選択は[現行運用手順](../../development-workflow.md)を参照する。[2026-10-21の実行報告](261021_lunapdf_test_cache_optimization_report.md)は当日の結果と測定値を記録した履歴資料である。

結果は、対象の検査ごとに次のいずれかで記録する。

- **実行して合格**：検査を実行し、対象範囲で期待した結果を確認した。
- **実行して失敗**：検査を実行し、失敗した。ログや対象範囲を併記する。
- **環境制約で未実施**：環境上実行できなかった。制約と未確認範囲を併記する。
- **実機未検証**：実機固有の確認をしていない。代替不能な理由と必要な確認範囲を記録する。

ヘッドレス検査や出力構造検査で実機固有の挙動まで確認したと扱わない。GUI実機確認が必要と判断した場合も、ユーザーの明示依頼がない間は実行せず、結果区分を「実機未検証」とし、GUIの未確認範囲を「GUI未検証」と明記する。
